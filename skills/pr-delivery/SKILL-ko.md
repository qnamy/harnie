# PR 전달 (PR 본문 · 리뷰요청 "무엇")

완성된 변경을 전달하는 산출물의 **내용(무엇)** 을 작성한다: PR 제목·본문, 그리고 리뷰요청 메시지 내용. **작성·판단만** 한다 — 실제 PR 생성 API·대상 브랜치·리뷰요청을 보낼 채널·멘션·필수 리뷰어 지정 같은 **"어떻게/어디에"는 호출자(플랫폼·루틴)가 회사 또는 플랫폼 지침에서 읽어** 수행한다. 회사·플랫폼 중립이다.

빌드 프로세스의 마지막 단계(…→ 개발리뷰 → **PR 생성 → 리뷰요청**). 산출된 PR은 이후 상대의 `pr-review` 대상이 된다.

## 입력 (호출자 제공)
- 변경(diff/커밋) + 빌드 맥락(해결한 문제·핵심 설계 결정·수행한 검증 증거) + (선택) 연결된 이슈/티켓.

## PR 본문 "무엇"
- **제목**: 무엇을 하는 변경인지 한 줄. 범위를 정확히(접두어·명명 규약이 있으면 호출자 지침).
- **요약**: 무엇을·왜(해결한 문제·의도). 추측이 아니라 실제 변경 근거로.
- **핵심 변경**: 리뷰어가 봐야 할 주요 변경점(파일/영역)과 **비자명한 결정의 근거**.
- **검증**: 어떤 검증을 어떤 tier로 수행했는지 — **수행한 것만** 쓴다. 못 한 검증은 미검증으로 정직하게 표기(꾸미지 않음).
- **범위·비목표**: 포함한 것 / **의도적으로 뺀 것**. 연결 이슈/티켓.
- 없는 사실을 지어내지 않는다. 불확실한 것은 열어둔다.

## 리뷰요청 "무엇"
- PR 참조(실제 URL은 호출자가 구성) + **무엇을·어디를 봐달라**(리뷰 초점).
- 리뷰에 필요한 **맥락**: 핵심 결정·트레이드오프·주의할 지점.
- **요청 종류** 명시: 일반 리뷰 / 고정밀 / 특정 관점(보안·성능 등).
- 간결하게 — 리뷰어가 바로 시작할 수 있게.

## 실행은 호출자 (회사 또는 플랫폼 지침)
PR 생성 방식(플랫폼 API/MCP)·대상 브랜치·리뷰어 지정 규칙(필수 리뷰어)·리뷰요청 채널·멘션은 환경 특화 설정이다. **해당 회사 또는 플랫폼 지침(예: 루틴 설정 파일)에서 읽는다.** 이 스킬은 그 좌표를 모른다.

## 출력
{ PR 제목, PR 본문(마크다운), 리뷰요청 메시지 내용, 리뷰 종류 }. 호출자가 이 내용을 받아 플랫폼에 PR 생성·리뷰요청을 실행한다.
