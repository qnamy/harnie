# PHASE B — Parallel Path (B2′–B3′)

It assumes you have already read `skills/dev-full/SKILL.md`'s Step 0, State Location, Delegation Reference Rule, Execution State/Mandatory Hooks, and Notepad Protocol sections, and `phases/phase-b.md`'s B1. ## Task Worktrees (State Location)

**Parallel PHASE B (task worktrees).** When B1 selects the parallel path, each task gets its own git worktree (`scripts/worktree.mjs create`), landing at `<repo>/.harnie-wt/<branch-with-slashes-dashed>` — for a task branch `harnie/<slug>-t<id>` that is `<repo>/.harnie-wt/harnie-<slug>-t<id>`, nested inside the **run worktree** (`<repo>` here is the same run workroot used everywhere else in this skill, per the Execution State section in `SKILL.md`, since `worktree.mjs`'s Bash-guard sanctioning requires `--repo` to equal the single active root). Only `.harnie-wt/` is registered in `.git/info/exclude` (by `worktree.mjs create`, idempotently) — `.harnie/` is **not**, and must not be: it is never committed to any branch in the first place (so a merge can never touch it regardless), and adding it to a gitignore-style exclude would make `delta.mjs`'s explicit-pathspec `git add` fail on an "ignored path" error. That task worktree is a **separate repo root** with its own `.harnie/`, holding only that task's pre-merge design (`.harnie/design/rev-N.md`) and review-loop state (`.harnie/review/design/`, `.harnie/review/code/`) — never `.harnie/plan/<slug>/…`, which stays exclusive to the run worktree. The task worktree carries no `execution.mjs` run state (no `active.json`, no manifest) — approval already happened once at A5 for the whole run, so nothing in PHASE B re-derives it per task.

> **Wave-2 integration update — gaps 1–3 below are resolved; gap 4 remains.** `scripts/guards.mjs` and `scripts/worktree.mjs` (owned by separate efforts) were updated directly for this, with a cross-model review round: verified via `node --test scripts/*.test.mjs hooks/*.test.mjs` and, for gap 3, by reproducing both the original failure and the fix in a throwaway repo.
> 1. **Codex-builder guard (`decideCodex`) now allows the active task worktree.** `cwd` may equal either the single active root or `<root>/.harnie-wt/harnie-<slug>-t<id>` for the run's active `<slug>` (via a new `isActiveTaskWorktree` helper) — any other path (wrong slug, wrong repo, one level too deep, a lookalike container name such as `.harnie-wt-evil/…`) is still denied exactly as before.
> 2. **`loop.mjs delta`/`apply` scoped to a task worktree are now recognized as sanctioned.** `guards.mjs`'s sanctioned-CLI check accepts `loop.mjs`'s repo/`--root` argument being either the single active root or the active task worktree (same helper as gap 1); once a call is sanctioned, `decideBash` returns before ever reaching the blanket Bash `.harnie` protection, so B2′ step 3's DR `apply` and step 5's CR `delta`/`apply` now go through despite pointing into `<taskWt>/.harnie/review/…`. `execution.mjs`'s and `worktree.mjs`'s own root/repo checks are deliberately unchanged — a task worktree carries no `execution.mjs` run state by design (see above), and `worktree.mjs create/merge/remove --repo` always names the run worktree that contains `.harnie-wt/`, never a task worktree itself.
> 3. **`worktree.mjs remove` now clears a task worktree's own `.harnie/` residue reversibly before removing it (B3′ step 5), narrowly.** It only attempts this when `<worktree>/.harnie/active.json`, `.../plan/`, and `.../quick/` are all absent (a task worktree never has any of these by design, only a run's own worktree does — this keeps an actual run's authority state, including mid-bootstrap, from ever being touched) *and* a `git status --porcelain` check first confirms every untracked/modified path in the worktree lies under `.harnie/`. Rather than deleting `.harnie/` outright, it moves it to a temporary, git-excluded stash directory, attempts the plain (no `--force`) `git worktree remove`, and only deletes the stash once that succeeds — on failure for *any* reason (dirty tree, a locked worktree, submodules, or anything else git might refuse for), `.harnie/` is moved back before the error is raised, so nothing is ever lost regardless of why removal failed. Genuinely unexpected untracked content outside `.harnie/` still blocks removal exactly as before. A path-containment assertion added to both `create` and `remove` also closes a `branch: ".."`-style traversal edge case surfaced during review.
> 4. **Builder-thread registration (`registerBuilderAuto`) still only tracks one concurrently-building task system-wide** (unchanged, out of this wave's scope) — `buildingUnboundTasks` requires exactly one `building`+unbound task to auto-bind a threadId. In practice this serializes only the **first** Codex call per task (the one bootstrapping its builder threadId), not all of B2′: mark a task `building`, make its first Codex call, wait for that call's threadId to register, *then* mark the next task `building` and make its first call. Once each task's threadId is registered this way, later `codex-reply` calls name that threadId explicitly, so the rest of B2′ (fix rounds, reviews) across different tasks can genuinely overlap in wall-clock time — only that initial per-task bootstrap moment is a serialization point.

> With 1–3 resolved, the parallel path works against the current, merged guard layer for every step in B2′/B3′/B4–B6, subject only to gap 4's narrow first-call serialization above. This skill still does not attempt any workaround beyond what's described above — disabling hooks, editing `guards.mjs`/`execution.mjs`/`worktree.mjs` outside a deliberate, reviewed change like this one, or hand-deleting `.harnie/` yourself would defeat the guard or corrupt state, not satisfy the invariant. If a step still fails or is denied for a reason other than gap 4, STOP and report it rather than bypassing it.

### Parallel path

**B2′. Per-task build (worktree-isolated; concurrency is bounded by the known dependency above — see its `registerBuilderAuto` note).** For each task, run the following independently — these can run concurrently across tasks once the dependency above is resolved; today, only one task's B2′ builder call (step 4) can have its threadId registered at a time:

1. **Create the task worktree.** `node <ROOT>/scripts/worktree.mjs create --repo <repo> --branch harnie/<slug>-t<id> --from harnie/<slug>` → stdout JSON `{worktreePath, created}`; `<taskWt>` = `worktreePath`. The branch point is the run branch (`harnie/<slug>`, i.e. the run worktree's own current branch). Calling `create` again for a branch that already has a worktree is idempotent — it returns `{worktreePath, created:false}` rather than erroring, as long as that worktree isn't already attached to a different branch.
2. **Task detailed design, lightweight.** Ask `harnie-designer` (read-only) for a **lightweight** detailed design scoped to this task only: inline `design-authoring-detail.md`'s Lightweight Output contract (do **not** signal "formal") and give it the run's approved `plan.md` architecture/detailed sections plus this task's manifest entry (id, scope, verification) as input. Write the result to `<taskWt>/.harnie/design/rev-1.md` — the same disk-artifact-of-record rule as PHASE A's Delegation Reference Rule (`SKILL.md`), scoped to the task worktree instead of `.harnie/plan/<slug>/`.
3. **Task design review, one loop, abridged by scope not by mechanism.** Run the design-review loop from `review-loop-driver.md`: producer = designer; reviewer = Codex (`sandbox:"read-only"`); criteria = `design-review.md`'s detailed-design lens; namespace `DR`; `<dir>` = `<taskWt>/.harnie/review/design/`. This is the same DR state machine as A4 (`phases/phase-a.md`), run to APPROVE — "abridged" describes the small, already-architected scope of a single task's lightweight design, not a shortcut around REJECT/REVISING. A REJECT still produces `rev-2.md` and a re-review.
4. **Build.** Run `execution.mjs set-task --root <repo> --slug <slug> --task <id> --run-status building` (same purpose as serial B2 ①: mark this task as the builder-bootstrap candidate), capture the baseline (`node <ROOT>/scripts/loop.mjs capture <taskWt>`), then delegate to the **Codex builder** through Codex MCP with `sandbox:"workspace-write"`, `approval-policy:"never"`, `cwd:<taskWt>`, and — where the caller can select a model — the **run-difficulty model** per `model-matrix.md` §3 (easy = `gpt-5.6-luna`, purely mechanical = `gpt-5.3-codex-spark`, medium = `gpt-5.6-terra`, hard = `gpt-5.6-sol`); otherwise the installation default. Include the task's manifest scope and the same six-section contract as B2, plus the **path** `<taskWt>/.harnie/design/rev-1.md` (or the latest `rev-N.md`) with an instruction to read it before implementing — unlike serial B2's run-root `.harnie/plan/<slug>/`, this path sits inside the builder's own `cwd` and holds only this task's pre-merge design, not run authority state, so pointing the builder at it does not cross the same boundary.
5. **Code review, pre-merge quality gate.** Capture the fix delta (`node <ROOT>/scripts/loop.mjs delta <taskWt> <baselineSHA> --scope <task-scope-paths> --out <taskWt>/.harnie/review/code/delta.patch`). Reviewer = read-only **`harnie-reviewer`**, never the builder's provider. Apply with `node <ROOT>/scripts/loop.mjs apply --root <taskWt> --ledger <taskWt>/.harnie/review/code/ledger.json --review <taskWt>/.harnie/review/code/round-N.txt --ns CR --state <taskWt>/.harnie/review/code/state.json --artifact <postSHA>`. REJECT → `codex-reply` fixes the delta only → re-review, same mechanics as B3 (`phases/phase-b.md`), until APPROVE.
6. **Commit the approved work — scoped to the task's declared paths, never a bare `-A`.** `loop.mjs`'s capture/delta operate on the working tree, not git history, so nothing above is a commit — but `worktree.mjs merge` (B3′) merges branches, which needs commits to exist. Once step 5 reaches APPROVE, in `<taskWt>`: `git add -A -- <the task's declared manifest `scope` paths>` then `git commit`. **Stage by scope path, not `git add -A -- . ":(exclude).harnie"` and not a bare `git add -A`** — `.harnie/` is not gitignored (see the note above on why it must not be), so either of those would stage this task's `design/rev-N.md` and review-loop bookkeeping right alongside the real source change (an exclude pathspec doesn't help here either: the literal text `.harnie` in a plain, non-sanctioned `git add` command is itself denied by the Bash guard's blanket `.harnie` protection — unlike step 5's `delta`/`apply`, this `git add` call is never a sanctioned CLI invocation, so the block still applies here), and `worktree.mjs merge` would then commit that `.harnie/` content into the run branch, permanently polluting the run worktree's tracked tree from that point on. Naming only the scope paths never mentions `.harnie` in the command at all, so nothing here trips the guard. Committing does not change the working tree, so it cannot invalidate step 5's `--artifact` check.

Before running this task's B3 confirmation round (B3′ step 4), append one entry per task to the run's `notepad.md`: its design-review and code-review verdicts and round counts. B3's confirmation round (`phases/phase-b.md`) reads this as prior context (see B3's parallel-path note there), and it is the only trace of the task-level review once the worktree is later removed (B3′ step 5) — a record, not a substitute for the confirmation round.

**B3′. Sequential integration, one task at a time.** As each task reaches APPROVE in B2′, integrate it into the run branch — one at a time, even when several tasks finished building in parallel; this is the one required serialization point. "One at a time" spans a task's **entire** B3′, steps 1–5, not just its merge: do not start the next task's step 1 (its baseline capture) until the current task's step 5 (worktree removal) is done — an in-progress task's unresolved state, if a second merge lands concurrently, would otherwise pollute that task's own confirmation-round delta as unattributed noise.

1. **Capture the run worktree's baseline and snapshot its authority, immediately before this task's merge:** `node <ROOT>/scripts/loop.mjs capture <repo>` (`<repo>` = the run worktree) → `mergeBaselineSHA` — this is the R1 baseline B3's confirmation round (step 4) will diff against, so capture it here, not earlier, or an earlier capture would include whatever the previous task's merge already landed. Then `node <ROOT>/scripts/execution.mjs seal --root <repo> --slug <slug>`. Seal **here, once, before the merge** — not later — because `execution.mjs`'s authority hash spans every `review/*/{ledger,state,receipt}.json` under `.harnie/plan/<slug>/`, and step 3's own conflict-resolution review (if any) legitimately writes a new one; sealing after that would make a later `seal-verify` see those legitimate writes as tampering.
2. `node <ROOT>/scripts/worktree.mjs merge --repo <repo> --branch harnie/<slug>-t<id> --into harnie/<slug>` (`<repo>`'s current checked-out branch must already be `into` — true by construction, since the run worktree always sits on its own branch). This runs `git merge --no-ff --no-edit` internally; stdout is JSON `{ok:true, conflicts:[]}` on success or `{ok:false, conflicts:[<paths>], stderr}` with exit 3 on conflict.
3. **Verify authority, then handle the merge result:**
   - **Clean merge (exit 0):** run `node <ROOT>/scripts/execution.mjs seal-verify --root <repo> --slug <slug>` once. `.harnie/` is never committed to any branch in the first place, so a merge can never touch it regardless of outcome — this call exists to catch anything else that touched authority state during this window, not the merge itself.
   - **Conflict (exit 3):** the merge is left unresolved with the conflicting files listed on stdout. **Capture a baseline now, at this conflicted state — before touching anything by hand**: `node <ROOT>/scripts/loop.mjs capture <repo>` → `resolveBaselineSHA`. (Capturing *after* resolving would diff the resolved tree against itself and produce an empty delta, silently approving a round that reviewed nothing.) Resolve by hand and commit the resolution, then run `execution.mjs seal-verify --root <repo> --slug <slug>` — the resolution only touched tracked source files, so this should pass; a mismatch means something else changed authority state and the round is invalid, same as everywhere else `seal-verify` is used. If it passes, run **one CR round on only the resolution's delta**: `loop.mjs delta <repo> <resolveBaselineSHA> --scope <paths the resolution touched> --out .../review/merge-t<id>/delta.patch`, then apply under `.harnie/plan/<slug>/review/merge-t<id>/` (same mechanics as B2′ step 5, rooted in the run worktree). Do not proceed to step 4 for this task until this round APPROVEs (and, per the header above, do not start the next task's B3′ either). **If the resolution touches a path inside an already-merged, already-confirmed earlier task's declared `scope`** (not just this task's), that earlier task's B4 receipt is now stale — re-run its B3 confirmation (fresh baseline captured now, delta scoped to that earlier task's declared `scope`, reviewed and applied into its own existing `<dir>`) and its B4 verify against the current tree before continuing; do not just reject/rebase the later task, since that alone leaves the earlier task's binding unrepaired.
   Either way, do not repeat `seal`/`seal-verify` at the start of step 4's B3 confirmation round below — this pair already satisfies its precondition (see B3's parallel-path note in `phases/phase-b.md`).
4. **Run this task's B3 confirmation round (in `phases/phase-b.md`), in the run worktree,** diffing from `mergeBaselineSHA` (step 1) to the current tree — which now includes the merge and any conflict-resolution commit from step 3. Do this **before** removing the task worktree (step 5): if it REJECTs, the fix goes back through the still-existing task worktree and its still-registered builder thread (see B3's parallel-path note in `phases/phase-b.md` — `codex-reply`, commit, re-merge, re-review), which needs nothing the engine doesn't already provide. Only proceed to step 5 once this round APPROVEs.
5. `node <ROOT>/scripts/worktree.mjs remove --repo <repo> --branch harnie/<slug>-t<id>` — no `--delete-branch` flag, since the default already keeps the branch. This now succeeds even though, by this skill's own design, every task worktree still has `.harnie/` content in it at this point (steps 2–3 write `design/rev-N.md` and `review/design/…`, step 5 writes `review/code/…`, none of it ever committed per step 6): `worktree.mjs remove` moves the task worktree's `.harnie/` to a temporary, git-excluded stash directory first, attempts the plain `git worktree remove`, and only deletes the stash once that succeeds — if removal fails for any reason (dirty tree, a locked worktree, submodules, or anything else git might refuse for), `.harnie/` is moved back before the error is raised, so nothing is ever lost regardless of *why* removal failed. If this still fails (for example genuinely unexpected untracked content outside `.harnie/`), STOP and report it rather than hand-deleting `.harnie/` (Bash `rm -rf` on a `.harnie` path is blocked the same way delta/apply are) or passing an unsupported flag.
