# PHASE B — Runner Path (B2′–B3′)

> Read this file from `phases/phase-b.md`'s B1, when the runner path applies (two or more tasks with disjoint scope — the default). It assumes you have already read `skills/dev-full/SKILL.md`'s Step 0, State Location, Delegation Reference Rule, Execution State/Mandatory Hooks, and Notepad Protocol sections, and `phases/phase-b.md`'s B1. Once every task's B3′ step 4 confirmation has APPROVEd, return to `phases/phase-b.md` for B4.
>
> On this path **you (main) do not run builds or unit reviews yourself**. Each task is owned end to end by one `harnie-task-runner` subagent in its own worktree; your job is briefs, spawning, sequential integration, and the gates. This is what keeps your context small: a runner's build/review rounds never enter your context — only its exit report does.

## Task worktrees (state location)

Each task gets its own git worktree on branch `harnie/<slug>-t<id>`, at `<repo>/.harnie-wt/harnie-<slug>-t<id>` (workspace runs: under the task's **member repo workroot** from the sentinel's `repos` registry). The task worktree is a separate repo root holding only that task's review-loop state (`.harnie/review/code/` — ledger, state, rounds, recorded baselines); never `.harnie/plan/<slug>/…`, which stays exclusive to the run workroot, and no `execution.mjs` run state (approval happened once at A5 for the whole run). `worktree.mjs create` registers `.harnie-wt/` in `.git/info/exclude` idempotently; `.harnie/` itself is never committed to any branch.

The guard layer sanctions all of this against the engine (`scripts/guards.mjs`, `scripts/worktree.mjs`, hooks): builder cwd may be any **building** task's own worktree (concurrent tasks included — the PostToolUse hook binds each builder threadId from its call's cwd), and `loop.mjs` accepts task-worktree roots. `worktree.mjs remove` **with `--archive-to`** preserves the task's review state (crash-safe, idempotent); **without the flag it deletes that state** (legacy/serial behavior) — on this path, always pass it. If a step is denied for a reason the docs do not predict, STOP and report — never work around a guard.

> **First-run environment check (canary, once per installation).** The runner path assumes the PostToolUse hook fires for subagent MCP calls and auto-binds each builder threadId from the call's cwd — verified for the local `mcp__codex__*` namespace (design §10), not yet for `mcp__plugin_harnie_codex__*`. On this installation's **first** runner-path run, do not batch-spawn: spawn a **single canary runner** (the smallest ready task) with the canary flag — its protocol performs a **binding handshake before any source-changing work** (a no-op workspace-write call, then it checks its own `builderThreadId` and exits `FAILURE: hook-binding-unverified` with a clean tree if unbound; see the runner's step 4b). On its exit report: **bound** → record the verified environment in `notepad.md`, batch-spawn the rest normally, never re-check. **`hook-binding-unverified`** → the tree is clean by construction, so: `node <ROOT>/scripts/worktree.mjs remove --repo <that task's repo workroot> --branch harnie/<slug>-t<id> --archive-to <repo>` (clean removal; empty review state archives as nothing), keep its `set-task building`, record the observation, and run the **entire run on the serial path** (B2–B3 — with the task worktree gone and a single building task, its root-cwd bootstrap self-binds); report so the design's fallback contract (§2 D2 대안) can be implemented before the next run.

## B2′. Per-task execution via runners (concurrent)

1. **Prerequisite: briefs exist** (written at A6). Each runner receives only its brief path — never the design document.
2. **Spawn by dependency level.** For every task whose manifest `deps` are all confirmed (B3′ step 4 APPROVE — not merely merged), in one batch: run `execution.mjs set-task --root <repo> --slug <slug> --task <id> --run-status building`, then spawn a `harnie-task-runner` subagent in the background with: task id, `<repo>` (the run workroot), the task's **repo workroot** (single-repo: `<repo>` itself; workspace: the member workroot from the sentinel's `repos` registry — the runner's git-tree operations all target this), `<ROOT>`, the brief path, the Codex model for the run difficulty (`model-matrix.md` §3), and — **on a respawn of a task whose thread is already bound — that `builderThreadId` from `execution.json`**. Pass the **unit-review tier** as the runner's Task model override (easy = sonnet, medium/hard = opus). Runners for independent tasks run concurrently; you continue with other work (integration of earlier tasks, monitoring) while they build.
3. **Collect exit reports.** Append each runner's verdict, rounds, threadId, and discoveries to `notepad.md` (single-writer rule — runners return content; only you append). A runner FAILURE report is triaged, not retried blindly:
   - **Builder infrastructure failure** (the runner's fail-fast: probe failure, or two identical idle-timeouts with a zero-change tree): stop spawning further builder work run-wide, notify the user, and recommend a session restart — the Codex MCP server is bound to this session's process, so respawning runners cannot recover it.
   - **Watchdog deny** (surfaced in the runner's report): you may self-extend **once per task** with `execution.mjs watchdog-extend --root <repo> --slug <slug> --task <id> --reason auto-cap` (engine-enforced: only before any other extension, total ≤ 2× the base budget), send a notification if a tool exists, and respawn the runner. Beyond the cap: report to the user and extend only with consent — same contract as the serial path's.
   - **STALLED**: surface to the user; after their decision, **you** re-run `loop.mjs apply` with `--reentry <reason>` (the runner never asserts re-entry), then respawn the runner.
   - Anything else: fix the stated cause (a bad brief path, a missing dependency) and respawn — the runner's resume table makes respawn safe at any interruption point.

## B3′. Sequential integration, one task at a time

As each task's runner reports APPROVE+committed, integrate — one at a time, spanning a task's **entire** B3′ (steps 1–5); do not start the next task's step 1 until the current task's step 5 is done.

1. **Baseline + seal, immediately before this task's merge:** `loop.mjs capture <task's repo workroot>` → `mergeBaselineSHA` (workspace runs: the member workroot — a `capture <repo>` of the run root returns the composite `ws:` artifact, which is a gate binding, not a delta baseline), then `execution.mjs seal --root <repo> --slug <slug>`. Seal here, once — step 3's conflict-resolution review legitimately writes review state, and sealing after it would read as tampering.
2. `worktree.mjs merge --repo <repo> --branch harnie/<slug>-t<id> --into harnie/<slug>` (workspace runs: `--repo` = the member workroot). Exit 0 = clean; exit 3 = conflicts listed on stdout.
3. **Clean merge:** run `seal-verify` once. **Conflict:** capture `resolveBaselineSHA` at the conflicted state **before touching anything**, resolve by hand, commit, `seal-verify`, then one CR round on only the resolution's delta under `review/merge-t<id>/`. If the resolution touched an earlier confirmed task's declared scope, that task's binding is stale — re-run its confirmation and verify before continuing.
4. **Confirmation round** (in `phases/phase-b.md` B3, parallel-path notes): delegate to `harnie-reviewer` at the confirmation tier, diffing from `mergeBaselineSHA`. On REJECT, the fix goes back through the still-existing task worktree and its registered builder thread (`codex-reply`, commit, incremental re-merge, re-review).
5. **Remove with archive:** `worktree.mjs remove --repo <repo or member workroot> --branch harnie/<slug>-t<id> --archive-to <repo>` — this moves the task's `.harnie/review/` into the run's `.harnie/plan/<slug>/review-archive/t<id>/` (validated against the active sentinel, manifest task, and repo registration; idempotent on re-run) before removing the worktree. The archive is the durable record of the task's unit review — `harness-digest` reads it, and the confirmation round's "prior verdict/rounds" context points at it. Never remove without `--archive-to` on this path.

## Design-defect corrections during execution (errata v2 propagation)

When a runner reports an `errata-candidate` (or you observe an approved-design defect yourself), follow `phases/phase-b.md`'s Design errata section: `errata-add`, and for blocker/degrade get the disposition user-approved via `errata-arm` + AskUserQuestion. Once a correction is approved, propagate by the brief's cited-sections header:

- **Affected set** = tasks whose briefs cite a corrected section, **plus their transitive manifest `deps` descendants**.
- *Unstarted:* reissue the brief as `t<id>-brief.v<N+1>.md` (new file; never overwrite) before spawning.
- *Runner in flight:* TaskStop it, reissue the brief, respawn — the resume table and its bound thread make this safe.
- *Built, unmerged:* fresh `capture --record` baseline → `codex-reply` the correction into the task worktree → delta review from that baseline.
- *Already integrated (worktree removed):* `execution.mjs rebind-task --root <repo> --slug <slug> --task <id> --reason correction:<E-NNN>` — this audit-logs the thread release and arms the `pendingRunRootBootstrap` marker (one at a time) — then a serial-path fix round in the run workroot (`phases/phase-b.md` B2/B3 mechanics, scope = that task's manifest scope; capture the baseline with `--record` into that task's reviewUnit dir **before** the bootstrap call). The engine binds the new thread only to the marker's task and only from a cwd whose git root matches that task's repo workroot. If the disk already carries the needed fix and the review APPROVEs without a new thread, close the marker with `rebind-task --cancel --task <id> --reason approved-artifact:<postSHA>`. Whole-tree changes mechanically invalidate already-APPROVEd Final Wave gates; completion forces their re-run.
- *Descendants (deps closure):* after the corrected ancestor's fix merges, re-run their B4 verify; escalate a descendant to a fix target only if its verify fails.

**Correction-round resume (marker states — judged from `execution.json` + the run tree, all yours to execute):**

| Observed | Re-enter |
|---|---|
| marker pending · task unbound · tree clean | re-issue the bootstrap codex call (the marker keeps designating until a bind succeeds) |
| marker pending · unbound · tree dirty (partial fix on disk) | delta from the recorded baseline → review the disk state as the producer output; REJECT → re-bootstrap noting the partial fix in the prompt; **APPROVE → close the marker: `execution.mjs rebind-task --root <repo> --slug <slug> --cancel --task <id> --reason approved-artifact:<postSHA>`**, then confirmation + verify |
| marker cleared · bound · dirty (died mid-fix) | normal REVISING resume via `codex-reply` on the bound thread |
| marker pending · bound | impossible (bind+clear is atomic) — STOP and report state corruption |
