# PHASE B — EXECUTE (Execution Phase)

> Read this file when entering PHASE B from `skills/dev-full/SKILL.md`. It assumes you have already read that file's Step 0, State Location, Delegation Reference Rule, Execution State/Mandatory Hooks, and Notepad Protocol sections — do not restate them here. This file covers B1 and the **serial path** (B2–B3), plus the steps common to **both paths** (B4–B6). For the **parallel path** (B2′–B3′), read `phases/phase-b-parallel.md` instead, then return here for B4.
>
> **Workspace runs (multi-repo):** wherever this file says "the run worktree" as a **git tree** — builder `cwd`, `loop.mjs capture`/`delta` targets, task-branch worktrees — substitute **that task's member repo workroot** (`<member repo>/.harnie-wt/harnie-<slug>`, from the sentinel's `repos` registry); a task's `repo` key names which one. Review-state paths (`<repo>/.harnie/plan/<slug>/review/…`), every `execution.mjs` call, and `loop.mjs apply --root` keep using the run workroot `<repo>`. The whole-run artifact for B5 gates is `loop.mjs capture <repo>` → `ws:<sha256>` (composite over all member workroots). Tasks in different member repos have disjoint scope by construction; the manifest's scope-disjointness validation (enforced at arm-approval) applies within each repo.

**B1. Parse the plan into tasks, assign each a file scope, and choose the execution path.** Every manifest task already declares `scope` (paths it may touch, see A4's `harnie-manifest` schema) — **paths only, not globs**: `loop.mjs delta`'s `outOfScope` check matches each changed path by exact equality or directory-prefix, not glob expansion, so a wildcard entry would flag every real change as out of scope. Task scopes are already **pairwise disjoint** — no path equal to, or a parent/child directory of, another task's `scope` entry within the same repo — because `validateManifest` enforces this at `arm-approval` (A5), where the manifest can still be revised; an approved manifest cannot carry an overlap, and B1 does not re-check it. (The check lives at A5, not here, because after approval the manifest changes only through A5.2's user-gated revision — a B1-time discovery would force that full re-approval.) Non-overlapping scope is a **precondition** for parallel execution, guaranteed by the approval gate, not a runtime guard.

Then pick the path:

- **Serial path — single task, or total scope small enough that parallel isolation buys nothing.** Continue with B2–B3 below exactly as written: no worktree, one builder, one review loop, directly in the run worktree.
- **Parallel path — two or more tasks with disjoint scope.** Read `phases/phase-b-parallel.md` now for B2′–B3′: each task gets its own isolated worktree, tasks build and review concurrently, then merge one at a time. A task whose manifest `deps` names another task starts only after that dependency's B3′ **step 4 confirmation APPROVEs** (not merely after its merge — a REJECT there can still change that task's code) — this is a single ordering rule the orchestrator applies by hand; do not build a scheduler, dependency-graph executor, or automatic retry for it. Once every task's B3′ step 4 has APPROVEd, return to this file for B4.

### Design errata — the in-run correction path for approved-design defects (run-wide, both paths)

When execution surfaces a defect in the **approved design itself** — the design document states something wrong — neither deviate from the design silently nor abandon the run. (A defect in the **manifest** — a wrong `timeout`, scope, or verification entry — is A5.2 territory, not errata.) Record it in the **append-only** errata file `.harnie/plan/<slug>/design/errata.md`. The mechanism that makes this work: once an entry's disposition is user-approved, **the review reference becomes the approved `design/rev-N.md` plus that entry's correction text** — the reviewer's agent body carries this rule, so a deviation covered by an approved entry is no longer a design-deviation issue, while a deviation with no approving entry stays REJECT.

- **Append-only, orchestrator-written.** Anyone in the loop surfaces a defect (builder report, reviewer issue, orchestrator observation); only the orchestrator appends. New findings get new `E-NNN` ids; never edit an existing entry — a correction to a correction is a new entry. Entry schema:
  ```
  ## E-NNN <one-line title>
  - found: <ISO time>, at <task/reviewUnit>
  - severity: blocker | degrade | note
  - design-ref: rev-N.md §<section>
  - defect: what the approved design got wrong + evidence
  - disposition: pending | approved-workaround (user approved <time>) | deferred-next-run | superseded-by-A5.2
  - correction: (appended when the disposition is set) what replaces the design statement — the reviewer judges against this text
  ```
- **Severity routing.** `note`: record and continue. `degrade`/`blocker`: stop building against the flawed statement, surface the entry to the user, and get the disposition approved via `AskUserQuestion` **before** any builder call that depends on it; until approved, related review issues stay open. (Safe alongside the approval gate: `recordPendingApproval` no-ops unless A5.1 has armed.)
- **Hard boundary — errata never touches the manifest.** It cannot expand a task's `scope`, change `verification`/`timeout` entries, or add/remove tasks. The moment a correction requires any of that, set `disposition: superseded-by-A5.2` and go through the user-gated manifest revision. Errata corrects **design prose only**.
- **Run-end teeth (v1, via the gate ledgers):** B5 passes the errata path to its gates, and the gate reviewer reports any `pending` blocker/degrade entry as an open blocking issue — so unresolved errata blocks completion through the normal ledger derivation, with no new engine capability. `deferred-next-run` entries are input to the next run's A1 grounding.

### Serial path

- **Watchdog contract.** On a watchdog deny, immediately report progress and blockers to the user and wait for instructions. Extend only after user consent, using `execution.mjs watchdog-extend --reason`. The per-task budget defaults to 30 min/15 builder calls and is tiered by the manifest's `difficulty` field (`hard` = 60 min/25) — review rounds consume the same wall clock as builds.

**B2. Delegate the task to a Codex builder (development producer = Codex).** Immediately before delegation, in order: ① run `execution.mjs set-task --root <repo> --slug <slug> --task <id> --run-status building` so hooks allow builder bootstrap; ② run `loop.mjs capture <repo>` to capture the baseline for the B3 R1 fix delta; ③ run `execution.mjs seal --root <repo> --slug <slug>` to snapshot authority. Then delegate to the **Codex builder** through Codex MCP with `sandbox:"workspace-write"`, `approval-policy:"never"`, `cwd:<repo>`, and the run-difficulty model (`model-matrix.md` §3: easy = `gpt-5.6-luna`, purely mechanical = `gpt-5.3-codex-spark`, medium = `gpt-5.6-terra`, hard = `gpt-5.6-sol`; installation default if model selection is unavailable). Include the task instructions and **the relevant approved design section from `plan.md`** so the builder implements the reviewed design. Require the six-section contract: requirements, brief design, implementation, robustness, tests, verification — summarized, not the full implementation source (see `review-loop-driver.md`). Also include the **builder delegation contract** standing rules from `review-loop-driver.md`: baseline-relative test evidence, fail-capability proof for new tests, and a preassigned build-tool cache path when the tool caches under the home directory. Keep scope surgical. **The builder must not access `.harnie/`**; authority state belongs to the orchestrator and CLI. The PostToolUse hook observes a successful Codex call and registers its threadId; use `codex-reply` for revisions.

**B3. ★ Code review loop, run worktree (cross-model; canonical review unit for completion — both paths land here).** Immediately after builder output and before delta attribution, run **`execution.mjs seal-verify --root <repo> --slug <slug>`**. If the builder accidentally altered authority files, fail closed, invalidate that round, and report it. If it passes, run R1–R5 from `review-loop-driver.md`:

- Producer = **Codex builder**. Reviewer = read-only **`harnie-reviewer` subagent** (model = the unit-review tier from `model-matrix.md` §3 — easy = sonnet, medium/hard = opus — passed as the Task model override where supported; its frontmatter default opus is the fallback), never main inline; this preserves cross-model review because the builder is Codex, and the reviewer cannot write. Criteria = `code-review.md` + `verification-tiers.md`. Namespace = `CR`. `<dir>` = `.harnie/plan/<slug>/review/<unit>/`, where `<unit>` is the task's manifest `reviewUnit`, **in the run worktree**.
- Record the reviewer's `review-schema.md` VERDICT/ISSUES response in `round-N.txt`. Pass **that round's delta `postSHA` through `--artifact` to `apply`**. This is mandatory for CR and lets `execution.mjs` recompute `reviewedScopeHash` at that tree, binding verification to the reviewed tree. For fixes, ask the Codex builder through `codex-reply`, then review only the delta. Continue until every dimension is APPROVE.
- **Parallel path** — same criteria, namespace, and `<dir>`, run per task in the run worktree:
  - **Timing:** after that task's B3′ merge lands (in `phases/phase-b-parallel.md`) but **before its task worktree is removed** — not immediately after its B2′ build, and not after the worktree is gone. This round, at this `<dir>`, is what `execution.mjs verify`/`completion` actually read; the pre-merge review inside the task worktree (B2′ step 5) is an earlier quality gate on isolated code, not a substitute for it.
  - **Baseline and scope:** R1 baseline = the `mergeBaselineSHA` captured in B3′ step 1, immediately before that task's merge, so the delta reviewed is exactly what the merge (and any conflict-resolution commit) introduced — nothing from a later task. Pass `--scope` covering the task's declared `scope` **plus** any path the conflict resolution touched outside it (B3′ step 3); omitting the latter makes `delta`'s `outOfScope` check misflag the resolution edit as an unattributed external change.
  - **Prior context:** give the reviewer the task's pre-merge verdict and round count (carried via the run's `notepad.md`, see B2′) so this pass can be an **abridged confirmation** — checking the merged result and anything the merge itself changed — rather than a full re-scan from zero. Model = the **confirmation-review tier** from `model-matrix.md` §3 (sonnet below hard): the logic was already gated at the unit-review tier, so this pass verifies the merge.
  - **No repeat seal-verify:** do not re-run `execution.mjs seal-verify` at the start of this round — B3′ step 3 already ran it once, before any review-round files existed; running it again here would hash the `merge-t<id>` ledger/state that step legitimately wrote and falsely report tampering.
  - **On REJECT:** the task worktree and its builder thread **still exist** (B3′ defers removal past this round to exactly enable this — see its step 5). Ask the same Codex builder through `codex-reply` to fix it there, commit the fix on `harnie/<slug>-t<id>` (same as B2′ step 6), then — capture before merge, same order as B3′ step 1 — capture a fresh `mergeBaselineSHA`, re-run `worktree.mjs merge` (a second, incremental merge bringing in just the new commit), and re-review the delta from that new baseline. This reuses the already-registered builder thread only; it needs no engine capability that bootstrapping a second builder for an already-bound task would require.

If a later task's delta touches a path an earlier, already-merged task also touched — an overlap the manifest's disjointness validation could not catch because it compares declared `scope`, not the actual diff — treat it as a scope overlap all the same: reject the later task's build, rebase its worktree onto the updated run branch, and re-review before merging.

### Both paths

**B4. Verify each task.** Run `execution.mjs verify --root <repo> --slug <slug> --task <id>`, in the **run worktree**, after that task's B3 confirmation. It executes the manifest's `verification[]` argv without a shell and records exitCode, scopeHash, and planHash receipts against reviewedPostSHA. Also perform Manual QA for user-visible behavior automation cannot catch, and reread `plan.md` to compare scope. Completion is rederived as **ledger APPROVE ∧ receipt pass**, so a failed verification or later code change automatically makes the task incomplete.

**B5. Final Wave (proportional to scale, parallel) — `Coverage · Quality · Runtime · Scope` gates.** Verify that the whole system fits together, in the run worktree — unaffected by whether B1 chose the serial or parallel path, since by this point all tasks are merged into one tree either way. Run each gate as an independent review unit through `review-loop-driver.md`, namespace `CR`, under `review/final-<gate>/` for `coverage`, `quality`, `runtime`, and `scope`:

- **Coverage** — Does the implementation satisfy every requirement ID and design decision in `plan.md`? Any uncovered FR/NFR is under-building.
- **Quality** — Apply the full `code-review.md` lens for correctness, safety, and overengineering.
- **Runtime** — Require actual execution evidence using `verification-tiers.md`, including integration boundaries. Unverified risk means REJECT.
- **Scope** — Complete only the requested scope and do not build unrequested work. Scope inflation is over-building and must be blocked.
- Reviewer = read-only **`harnie-reviewer`**, the opposite provider from the Codex builder, at **opus regardless of run difficulty** (`model-matrix.md` §3 — the Final Wave is the last line of defense and is bounded at 4 units). For each gate, pass the current tree's `--artifact <postSHA>` to `apply`. Require every gate to APPROVE, rerunning **only failed gates**. Use Claude alone by default; if the user requests high precision, add an auxiliary dual-provider final sign-off from Codex.
- **Design errata wiring:** if `design/errata.md` exists, pass its path in every gate's prompt — approved entries are part of the review reference, and the gate reviewer must report any `pending` blocker/degrade entry as an open blocking issue (see the Design errata section above).

**B6. Report and rederive completion.** Run `execution.mjs completion --root <repo> --slug <slug>` to traverse the manifest and rederive completion. Each task requires ledger APPROVE, receipt pass, and current scope matching reviewed scope; each gate requires an approved ledger and the current whole tree matching the reviewed tree. Summarize changed files, each task's tier and verification evidence, every review unit's final verdict and round count, and all four Final Wave verdicts. If `design/errata.md` exists, include an errata digest — ids, severities, dispositions — and count any `pending` blocker/degrade entry among the remaining blockers of an honest INCOMPLETE report. **End the final response with a machine-readable footer:** if rederived complete, `HARNIE_STATUS: COMPLETE`; otherwise `HARNIE_STATUS: INCOMPLETE — <remaining blocker summary>`. The Stop hook uses the same derivation, so it blocks exit when authority says incomplete but the response claims COMPLETE or omits the footer. Report remaining blocking units, STALLED units, and unverified scope honestly as INCOMPLETE, then return control to the user.
