# PHASE A — PLAN (Planning Phase)

> Read this file when entering PHASE A from `skills/dev-full/SKILL.md`. It assumes you have already read that file's Step 0, State Location, Delegation Reference Rule, Execution State/Mandatory Hooks, and Notepad Protocol sections — do not restate them here.

**A0. Adopt the active run (do not self-init).** Resolve `<repo>` to the run workroot from the bootstrap hook's context message or, if needed, `<main repo>/.harnie/sessions/<this session's id>.json`. The hook already created `<repo>/.harnie/active.json` and `execution.json` there for this invocation (phase `planning`). Read that workroot's `.harnie/active.json`, confirm `track === "plan"`, and use its `slug` throughout. If it is absent or malformed, STOP and report the bootstrap failure — never run `execution.mjs init` to recover. With the sentinel present, mandatory hooks block pre-approval source writes, write-capable subagents, and `workspace-write` Codex calls. If the context message is flagged `WORKSPACE run`, also read the workspace-run rules in `SKILL.md`'s Execution State section — they change where scope, verification, builders, and capture operate throughout both phases.

**A0.5 (workspace runs only). Register member repos before the approval gate.** As A1's grounding identifies which repos under the workspace this task actually modifies, register each one: `node <ROOT>/scripts/execution.mjs repo-add --root <repo> --repo <absolute repo path>`. Record the returned `{key, workroot}` pairs in `plan.md`; every manifest task must later name its `"repo": "<key>"` from this set, and `arm-approval` fails closed on an unregistered key. Registration is idempotent — re-running for the same repo attaches to the existing worktree.

Finally, fix the **run difficulty**: inherit the easy/medium/hard the `/harnie:dev` router announced, or judge it now with the rubric in `${CLAUDE_PLUGIN_ROOT}/instructions/model-matrix.md` §2 on direct entry. Announce it and record it in `plan.md` (for example a `## Run Difficulty` line). Judged once, fixed for the run; it tiers **producer** models below (A4 designer, B2/B2′ builder) and the code reviewer conservatively (`model-matrix.md` §3 — Final Wave gates always opus). Also record it later as the manifest's top-level `difficulty` field (A4's `harnie-manifest` block): the execution watchdog tiers its per-task budget from it (`hard` raises the default 30 min/15 builder calls to 60 min/25 — review rounds share the same wall clock).

**A1. Ground with a scope-proportional investigation.** Spawn `harnie-scout` (haiku) **in parallel** to investigate. For each dimension below, first confirm whether it **exists and is relevant** to this task, then trace only the relevant ones deeply — forcing deep investigation of unrelated areas is scope inflation:

- the affected code and its **call paths** (callers and callees),
- existing **tests** covering the area,
- **configuration and environment variables**,
- **data/schema and migrations**,
- **external integrations and APIs**,
- relevant **docs/ADRs and repo guidance** (`AGENTS.md`, `CLAUDE.md`, `README`, and team conventions),
- **similar existing implementations** whose conventions to mirror,
- **prior runs' design errata** (`design/errata.md` under earlier runs' `.harnie/plan/*/`, when present) — defects already found against approved designs of this area, especially `deferred-next-run` entries, so this run's design does not repeat them.

Ground every decision in actual files, interfaces, dependencies, and conventions before assuming. Record the environment facts the design will depend on — the Environment Fact Sheet categories in `design-authoring-detail.md` (schema-migration head, test infrastructure and baseline test failures, runtime configuration constraints, framework/build-tool behavior) — in a `## Environment Fact Sheet` section of `plan.md`, each fact with its source path.

**A2. Decide questions by evidence — not by a CLEAR/UNCLEAR label.**

- **Do not ask** what you can confirm or reasonably infer from code, tests, config, or docs. Investigate first (A1).
- **Ask only** when the answer is not derivable and a wrong guess is costly, limited to: (a) **product or policy intent that only the user can decide** (behavior, UX, or tradeoffs encoded nowhere); (b) an ambiguous requirement with **materially different valid interpretations**; (c) a decision that would cause **significant rework or a compatibility break** if guessed wrong; (d) **external context you cannot infer** — a credential **source/configuration**, target, or account (ask for the source/config only; never request secret values).
- **Before asking**, present the evidence you gathered, **the parts you could not confirm**, the options with **each option's impact**, and your **recommended default with the WHY**.
- **Batch limit**: at most **3 questions in a single design-discovery round**; no omnibus/compound questions. (The A5 approval question is separate and not counted here.)
- For each **unresolved but non-blocking** uncertainty (not every non-asked detail), adopt a best-practice default and **record it in a `## Assumptions` section of `plan.md`** — not just announce it — so the design review and approval gate can see it.

**A3. Formal architecture design + review loop (conditional).** Ask `harnie-designer` — model **fable**, per `model-matrix.md` §3: the ARCH altitude always uses the top design tier regardless of run difficulty. Pass it as the Task model override where the installation supports it; if fable cannot be selected, fall back to opus and note the substitution in `plan.md`. Ask it for a **formal architecture design**. Pass the **absolute path** to `${CLAUDE_PLUGIN_ROOT}/instructions/design-authoring-arch.md` in the delegation prompt and signal `architecture, formal`; the designer's agent body requires it to Read that profile before writing, so do not paste the contract into the prompt. Focus on system boundaries, data ownership, technology choices, and SPOFs; do not descend into classes or SQL. Name the destination path `.harnie/plan/<slug>/design/rev-N.md` in the delegation; **the designer writes the design there directly** (see the Delegation Reference Rule) and returns a short summary. Verify the file exists and is non-empty **before any delegation that references it**, and record the same revision in the architecture section of `plan.md`.

- **A3 trigger checklist — run this stage iff at least one holds; otherwise skip to A4:** ① a new component, module, or service is introduced; ② a boundary or cross-module/cross-repo contract changes; ③ a data-ownership or storage choice is made; ④ a technology is selected or replaced; ⑤ an SPOF, scaling, or availability decision is taken. If the existing architecture remains intact and the work is a large detailed change within it, skip to A4. An unsupported formal architecture stage is scope inflation. (These same triggers define the ARCH altitude that routes a task to the plan track at all — `model-matrix.md` §1.)
- When run, continue through the **architecture design review loop** to APPROVE using `review-loop-driver.md`: producer = designer; criteria = the **architecture-altitude lens** in `design-review.md` (boundaries, ownership, technology choices, SPOFs); namespace `DR`; `<dir>` = `.harnie/plan/<slug>/review/design-arch/`. Instead of the R1 delta, **pass the `design/rev-N.md` path** to the Codex reviewer with an instruction to read it before reviewing — the path alone for the first review; the path plus the list of changed section names for rereview; R2–R5 remain unchanged.
- Each revision that answers a review round is a **new `rev-N.md`**, written before the re-review is delegated. Never re-review a revision by pointing at the previous file or at a tool-result blob.

**A4. Formal detailed design + review loop.** On top of the approved architecture or existing architecture, ask `harnie-designer` (model by run difficulty per `model-matrix.md` §3: easy/medium = sonnet, hard = opus — pass it as the Task model override where supported; otherwise its frontmatter default `opus` applies) for a **formal detailed design**. Pass the **absolute path** to `${CLAUDE_PLUGIN_ROOT}/instructions/design-authoring-detail.md` in the prompt and signal `detailed design, formal`; the designer's agent body requires it to Read that profile first. Also pass `plan.md`'s path naming its `## Environment Fact Sheet` section so the designer starts from A1's verified facts instead of re-deriving or assuming them. Require a requirements traceability table, key processing logic, contracts, data/state, and work breakdown at a decision-complete level. Do not silently change architecture decisions; if one must change, return to A3 and request an architecture revision. Name the next `.harnie/plan/<slug>/design/rev-N.md` as the destination in the delegation; **the designer writes it there directly** and returns a short summary. Verify the file exists and is non-empty before delegating anything that references it, and record the same revision in the detailed section of `plan.md`.

- Run a **detailed-design review loop** independent of A3, with a separate ledger/state: producer = designer; criteria = the **detailed-altitude lens** in `design-review.md` (decision completeness, requirements coverage, failure modes); namespace `DR`; `<dir>` = `.harnie/plan/<slug>/review/design-detail/`. As in A3, **pass the reviewer the `design/rev-N.md` path** (path alone on first review; path + changed section names on rereview) instead of an R1 git delta, because design files live under `.harnie/` and are excluded from delta handling.
- Both loops exist to catch design errors **before implementation**. Report STALLED to the user. Architecture and detailed design are reviewed independently, in that order.
- **Order of reflection on a review finding — answer two questions before writing any fix (both loops).** For each REJECT issue, in this order: ① Is the threat or failure it assumes **inside the threat model** (`§0.1`: a fallible, over-eager orchestrator or builder making mistakes — a session-adversarial main agent is a non-goal)? ② **Must a new mechanism exist for it**, or is it already covered by something the design already has? Only after both answers do you write how to satisfy the issue. Taking each REJECT as "how do I satisfy this?" alone is what accumulates claims, leases, receipts, and hash identifiers across revisions and costs several rounds to unwind.
- **A fix that adds a mechanism must carry its justification:** at least one **concrete mistake scenario** it prevents, recorded in a `## Revision Notes` section of the new `design/rev-N.md`. If you cannot state one, do not add the mechanism — instead answer the reviewer in the next round with both answers above and ask it to **drop the blocking demand**. The ledger moves only through the reviewer's next response, and only in the shape `mergeLedger` accepts: it **closes the original ID as `resolved`** (the risk no longer applies under the current scope and decisions) and, if the concern is still worth recording, **opens a new `non-blocking` ID**. Re-labeling the same ID from blocking to non-blocking fails closed in `scripts/ledger.mjs`, so never ask for it and never hand-edit `ledger.json` or the verdict.
- **Machine-parsable manifest block (approval artifact):** After the detailed design's work breakdown is final, add a JSON block fenced with ` ```harnie-manifest ` to `plan.md`: `{difficulty?, tasks:[{id, deps, reviewUnit, scope:[<paths>], setup?:[{executable, args, cwd, timeout}], verification:[{executable, args, cwd, timeout}]}], gates:[{name, reviewUnit}]}` (`difficulty` = the A0 run difficulty, `easy|medium|hard` — tiers the execution watchdog budget). Every task and gate `reviewUnit` must be unique and becomes its review-directory name. `scope` lists paths the task may touch; task `scope`s must be **pairwise disjoint** within a repo — no entry equal to, or a parent/child directory of, another task's entry — and `arm-approval` fails closed on an overlap, since after approval fixing the manifest costs a full A5.2 revision (user re-approval). `timeout` is in **milliseconds** — it is passed to `spawnSync` unchanged, so a seconds value (e.g. `60`) kills every run of that entry at 60ms; `arm-approval` rejects values under 1000 as a suspected unit mistake. `verification` contains shell-free argv for mandatory runtime evidence (optional `evidencePolicy: "exit-code-only"` for tools that are silent on success; default `output-required`); **every entry must survive the A5.0 evidence check below before it is registered**. `setup` (optional) lists shell-free **warm-up** argv that `verify` runs once, in order, immediately before `verification[]` — dependency installs and cold-start compiles (e.g. a first `uv run pytest` building C extensions) that would otherwise consume any reasonable verification `timeout`. Setup output is never verification evidence and skips vacuous detection; a non-zero setup exit fails the receipt without running `verification[]`; setup must not modify scope sources (the same scopeHash invariant applies) and takes no `evidencePolicy`. Gates are the four Final Wave units—`coverage`, `quality`, `runtime`, and `scope`—with `reviewUnit` values `final-<name>`. At A5 approval, this block is frozen as `manifest.json` and sealed by planHash as the authority set — immutable except through the user-gated revision path in A5.2.

- **Review-unit granularity (merge small waves):** every task is a full build+review loop with fixed overhead — builder session bootstrap, reviewer criteria/design reads, R1–R5 wiring, its own ledger/state — so a task too small to justify that cost is waste, not rigor (measured runs paid the full loop for minutes-long units). When forming the manifest from the design's work breakdown, fold a trivially small piece (a config touch, a notification hook, a few dozen low-risk lines) into the most related adjacent task instead of giving it its own `reviewUnit`. Keep a separate task only when it earns one: independent risk worth its own ledger, a `deps` ordering other tasks wait on, or isolation value on the parallel path. Granularity is decided here, once — after approval, splitting or merging costs an A5.2 revision.

**A5. Approval gate (once, bound to the real approval tool).**

**A5.0 — Prove every verification command actually exercises something, before registering it (required, before arming approval).** The manifest's `verification[]` entries are the only runtime evidence `verify` will ever produce, so an entry that exercises nothing passes forever while verifying nothing. Pre-approval Bash is restricted to read-only commands by H1, so prove each entry the strongest way that gate allows and record the result next to the manifest block in `plan.md`:

- **Read-only query entries** (`rg`, `grep`, `git ls-files`, `jq`, …): run the argv **exactly as written**, once. Record `exitCode` and the **match count**. 0 matches → do not register it.
- **Entries needing an interpreter or test runner** (`node --test`, `npm test`, `tsc --noEmit`, …): these **cannot** run before approval, and **do not loosen the gate to make them run** — executing repo code pre-approval is precisely the write primitive H1 blocks. Instead prove the **input set** with a read-only discovery command (list the files the runner's own pattern would collect) and record the count; 0 means the entry verifies nothing. The silent case is a **pattern argument that matches nothing**: `node --test 'scripts/*.test.mjs'` with no matching file reports `# tests 0` and **exits 0** (verified on Node v21.6.2). Since manifest argv is shell-free, such a pattern reaches the runner literally — so list the matches first, and prefer an argv whose inputs you have enumerated.
- **Empty is not the same as silent.** `tsc --noEmit`, quiet linters, and schema validators print nothing on success; that is a pass, not empty evidence. **Empty means the command exercised nothing**: 0 matches, 0 tests collected, 0 files checked. For a silent-success tool, take the exercised count from the tool itself (its file-list or verbose flag, or a reported input count) rather than from output size — and declare `evidencePolicy: "exit-code-only"` on that manifest entry so the engine's output-evidence check (default `output-required`) does not flag its intended silence.
- **Cold starts belong in `setup`, not in an inflated timeout.** If a verification command's first run must install dependencies or build extensions (e.g. `uv run pytest` bootstrapping a venv with C-extension packages), no honest `timeout` covers the cold run without also masking a hung warm run. Declare the warm-up as a `setup` entry (same argv shape, run before the timed verification) and size `verification[].timeout` for the warm case.
- **Timeout unit sanity.** `timeout` is **milliseconds**. The engine rejects values under 1000 at arm time, but a plausible-looking wrong value still passes that floor — `1800` meaning "30 minutes" is 1.8 seconds and will kill any real test run. For each entry, estimate the command's realistic worst-case runtime, write the milliseconds out in full (e.g. 10 minutes = `600000`), and record the estimate next to the A5.0 evidence.
- **The engine backstops this gate, but cannot repair it.** `verify` captures each entry's output and runs vacuous-success detection ([execution.mjs:138](scripts/execution.mjs:138)): exitCode 0 with zero output, `node --test` passing 0 tests, or a search command with 0 matches marks the receipt `vacuous`, and completion rejects a vacuous receipt as a blocker ([execution.mjs:173](scripts/execution.mjs:173)). The backstop only turns a hollow entry into a hard block, not into a repair path: after approval the manifest changes only through the **A5.2 revision path** — a full user re-approval — so a vacuous entry costs another approval round-trip and re-verification of every task. Get it right here.

Traps worth a few seconds each: `rg -e A -e B` is **OR**, not AND; `rg --files-without-match` inverts the polarity you probably meant. A command that cannot fail is not verification.

**A5.1 — Ask for approval.** Present the review-approved `plan.md`, including architecture and detailed design, work breakdown, verification strategy with its A5.0 evidence, Final Wave, and `harnie-manifest` block. Then ① run `execution.mjs arm-approval --root <repo> --slug <slug> --approve-option "Approve"`, and ② **immediately** ask the approval question with `AskUserQuestion` — this must be the very next `AskUserQuestion` call after arming, since the hook binds to the **first** one observed (a one-shot consumption, not a text match against the armed question), so any other question asked in between would consume the slot instead and leave approval stuck. Option labels must make approval and rejection distinguishable by selected value alone, such as `Approve` / `Reject or revise`. PreToolUse records that call's tool_use_id and the current planHash as pending; PostToolUse binds only if the selected value is exactly `Approve` and planHash is unchanged, opening `phase=executing`. This prevents an over-eager main agent from self-approving or changing the plan after asking. `set-phase` cannot enter executing. Rejection or a planHash mismatch fails closed and remains `awaiting-approval`. After approval is confirmed, enter PHASE B (read `phases/phase-b.md`). A3 and A4 already provide design-soundness gates, so approval normally occurs once — A5.2 below is the only exception.

**A5.2 — Manifest revision (post-approval repair, user-gated).** If a manifest defect surfaces after approval (a wrong `timeout`, a hollow verification entry, a scope error), the run does not have to be abandoned. Fix the `harnie-manifest` block in `plan.md` — the planHash change automatically invalidates the standing approval, so hooks treat the run as `awaiting-approval` again — then re-run A5.1 (arm + `AskUserQuestion`). On the new approval, the engine archives the previous manifest as `manifest.v<n>.json` (audit trail; itself a protected control file) and replaces `manifest.json` under the new planHash; `execution.json` and the sentinel follow. Plan for the consequences: existing verification receipts carry the old planHash, so completion re-derivation forces `verify` to be re-run for every task (review ledgers and their APPROVEs survive), and re-seal before the next builder or review round as usual. This path is deliberately expensive — a full user re-approval — so A5.0 diligence remains the cheap path; never treat A5.2 as a routine edit channel.
