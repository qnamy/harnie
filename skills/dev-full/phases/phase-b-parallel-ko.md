# PHASE B — 병렬 경로 (B2′~B3′)

> `phases/phase-b.md`의 B1에서, 병렬 경로가 적용될 때(태스크 ≥2개이고 스코프가 비중첩) 이 파일을 읽는다. `skills/dev-full/SKILL-ko.md`의 Step 0·상태 위치·위임 참조 규칙·실행 상태/강제 훅·Notepad 프로토콜 섹션과 `phases/phase-b.md`의 B1을 이미 읽었다고 전제한다. 아래 모든 태스크의 4단계가 APPROVE되면 `phases/phase-b.md`로 돌아가 B4를 진행한다.

## 태스크 Worktree (상태 위치)

**병렬 PHASE B(태스크 worktree).** *(워크스페이스 run: phase-b-ko.md의 대체 주석을 여기도 적용한다 — **git tree로서의 `<repo>`**는 task의 멤버 repo workroot를 뜻하므로, task worktree는 `<member workroot>/.harnie-wt/harnie-<slug>-t<id>`에 생기고, `worktree.mjs --repo`는 그 멤버 워크루트를 지명한다. guard layer는 등록된 멤버 워크루트와 그 task worktree를 활성 루트 옆에 sanctioned로 인정한다.)* B1이 병렬 경로를 선택하면 태스크마다 git worktree(`scripts/worktree.mjs create`)를 갖는다 — `<repo>/.harnie-wt/<브랜치의 슬래시를 대시로 바꾼 이름>`에 생성되며, 태스크 브랜치 `harnie/<slug>-t<id>`라면 `<repo>/.harnie-wt/harnie-<slug>-t<id>`다. **run worktree 안에 중첩된다**(여기서 `<repo>`는 `SKILL.md`의 실행 상태 절에서 쓰는 것과 같은 run workroot다 — `worktree.mjs`의 Bash-가드 sanction이 `--repo`가 단일 활성 루트와 같을 것을 요구하므로). `.git/info/exclude`에는 `.harnie-wt/`만 등록된다(`worktree.mjs create`가 멱등하게) — `.harnie/`는 등록하지 **않는다**: 애초에 어떤 브랜치에도 커밋된 적이 없으므로(그래서 merge가 그걸 건드릴 수 없다), gitignore식 exclude에 넣으면 `delta.mjs`의 명시적 pathspec `git add`가 "ignored path" 오류로 실패한다. 그 태스크 worktree는 **별개의 repo 루트**로 자기만의 `.harnie/`를 가지며, 그 태스크의 머지 前 설계(`.harnie/design/rev-N.md`)와 리뷰 루프 상태(`.harnie/review/design/`, `.harnie/review/code/`)만 담는다 — `.harnie/plan/<slug>/…`는 절대 아니며, 그 경로는 run worktree 전용으로 남는다. 태스크 worktree는 `execution.mjs` run 상태(`active.json`·manifest)를 전혀 갖지 않는다 — run 전체 승인은 A5에서 이미 1회 끝났으므로, PHASE B에서 태스크마다 다시 재도출하지 않는다. 가드 계층이 이 모든 것을 engine(`scripts/guards.mjs`, `scripts/worktree.mjs`, hooks)에 대해 sanctioned로 처리한다: builder cwd는 어떤 **building** 태스크의 자신 worktree든 가능하고(concurrent 태스크 포함 — PostToolUse 훅이 각 호출의 cwd에서 각 builder threadId를 bind함), `loop.mjs`는 task-worktree roots를 받아들인다. `worktree.mjs remove` **`--archive-to` 플래그 있으면** 태스크의 리뷰 상태를 보존한다(crash-safe, 멱등). **플래그 없으면 그 상태를 삭제**한다(legacy/직렬 동작) — 이 경로에선 항상 플래그를 넘겨야 한다. 예측할 수 없는 이유로 어떤 단계가 거부되면 우회하지 말고 STOP하고 보고한다.

> **First-run environment check (canary, 설치당 1회).** runner path는 PostToolUse 훅이 subagent MCP 호출에 대해 발화되고 각 빌더 threadId를 호출의 cwd에서 자동 바인딩한다고 전제한다 — 로컬 `mcp__codex__*` 네임스페이스(설계 §10)는 검증됐지만 `mcp__plugin_harnie_codex__*`는 아직 안 된다. 이 설치의 **첫** runner-path run에서는 batch-spawn을 하지 말고, **단일 canary runner**(가장 작은 준비된 태스크)를 canary 플래그와 함께 spawn한다 — 그 프로토콜은 소스를 바꾸는 어떤 일 前에 **binding handshake를 수행**한다(no-op workspace-write 호출, 그다음 자기 `builderThreadId` 확인 후 unbound면 clean tree 상태에서 `FAILURE: hook-binding-unverified`로 exit). exit report를 보고: **bound** → 환경 검증을 notepad.md에 기록하고, 나머지 batch-spawn을 정상적으로 하며, 다시 검사하지 않는다. **`hook-binding-unverified`** → worktree가 설계상 clean이므로: `node <ROOT>/scripts/worktree.mjs remove --repo <그 태스크의 repo workroot> --branch harnie/<slug>-t<id> --archive-to <repo>`(깨끗한 제거; 비어있는 리뷰 상태는 아무것도 archive하지 않음), 그 `set-task building` 상태는 유지하고, 관찰을 기록한 후 **전체 run을 직렬 경로로**(B2–B3 — task worktree가 사라졌고 building task 하나이므로 그 root-cwd bootstrap이 self-bind된다) 실행한다. 설계의 폴백 계약(§2 D2 대안)이 다음 run 前에 구현될 수 있도록 보고한다.

### 병렬 경로

**B2′. 태스크별 실행(runner 경유; 동시성은 위 알려진 의존성에 의해 제한됨).**

1. **전제: brief 존재.** 각 runner는 오직 그 brief 경로만 받는다 — design document는 받지 않는다.
2. **의존성 레벨로 spawn.** manifest `deps`가 모두 확인된(B3′ step 4 APPROVE — merge만으로는 부족; 거기서 REJECT면 그 태스크 코드가 다시 바뀔 수 있음) 모든 태스크에 대해 한 batch로: `execution.mjs set-task --root <repo> --slug <slug> --task <id> --run-status building` 실행, 그 다음 background에서 `harnie-task-runner` subagent spawn — 태스크 id, `<repo>`(run workroot), 태스크의 **repo workroot**(단일-repo: `<repo>` 자신; workspace: sentinel의 `repos` registry에서의 멤버 workroot — runner의 모든 git-tree 작업이 이것을 대상으로 함), `<ROOT>`, brief path, 모델(run difficulty에 따라 `model-matrix.md` §3), 그리고 — **스레드가 이미 바인딩된 태스크 respawn 시에만 — 그 `builderThreadId`를 `execution.json`에서**. runner의 Task 모델 오버라이드로 **unit-review tier** 넘김(easy = sonnet, medium/hard = opus). 독립적인 태스크의 runner는 concurrent 실행; 당신은 다른 작업(earlier task 통합, monitoring)을 계속한다.
3. **Exit report 수집.** 각 runner의 verdict·라운드·threadId·발견을 `notepad.md`에 append(single-writer — runner는 content만 반환, 당신만 append). Runner FAILURE는 triage 대상:
   - **Builder infrastructure failure**(runner의 fail-fast: probe failure 또는 zero-change tree로 두 번의 identical idle-timeout): 더 이상 builder 작업 spawn 금지, 사용자 알림, 세션 restart 권고 — MCP 서버는 이 session의 process에 bound.
   - **Watchdog deny**(runner의 report에 surface): 태스크당 **1회 self-extend** 가능: `execution.mjs watchdog-extend --root <repo> --slug <slug> --task <id> --reason auto-cap`(engine-enforced: 다른 연장 前에만, 총 ≤2배), notification 보내고 runner respawn. 한도 이상: 진행상황 보고하고 consent 있을 때만 연장.
   - **STALLED**: 사용자에게 surface; 그들의 결정 후 **당신이** `loop.mjs apply --reentry <reason>` 실행, runner respawn.
   - 그 외: 진술된 원인 고치기(bad brief path, 빠진 dependency)하고 respawn — resume table이 어떤 interruption point에서든 respawn을 safe하게 함.

1. **태스크 worktree 생성.** `node <ROOT>/scripts/worktree.mjs create --repo <repo> --branch harnie/<slug>-t<id> --from harnie/<slug>` → stdout JSON `{worktreePath, created}`; `<taskWt>` = `worktreePath`. 분기점 = run 브랜치(`harnie/<slug>`, 즉 run worktree 자신의 현재 브랜치). 이미 그 브랜치의 worktree가 있으면 `create`는 멱등하다 — 다른 브랜치에 이미 붙어 있는 게 아닌 한 에러 대신 `{worktreePath, created:false}`를 돌려준다.
2. **태스크 상세설계, 경량.** `harnie-designer`에게 이 태스크 하나만의 **경량** 상세설계를 요청한다 — `design-authoring-detail.md`의 Lightweight Output 계약을 인라인 주입("formal" 신호 **금지**), run의 승인된 `plan.md` 아키/상세 섹션 + 이 태스크의 manifest 항목(id·scope·verification)을 입력으로 준다. 목적지 경로로 `<taskWt>/.harnie/design/rev-1.md`를 지명한다; **designer가 거기에 직접 쓰고** 짧은 요약을 반환한다 — PHASE A 위임 참조 규칙(`SKILL.md`)과 동일한 디스크-정본 원칙을, `.harnie/plan/<slug>/` 대신 태스크 worktree로 스코프만 바꿔 적용.
3. **태스크 설계 리뷰, 1 루프, 스코프만 축약이지 기구는 축약 아님.** review-loop-driver.md의 설계 리뷰 루프를 돌린다: producer=designer, 리뷰어=Codex(`sandbox:"read-only"`), 기준=design-review.md 상세 고도 렌즈, namespace `DR`, `<dir>`=`<taskWt>/.harnie/review/design/`. A4(`phases/phase-a.md`)와 **같은 DR 상태기계**를 APPROVE까지 돌리는 것이다 — "축약"은 이미 아키가 확정된 단일 태스크의 경량 설계라는 **작은 범위**를 뜻하지, REJECT/REVISING을 건너뛰는 지름길이 아니다. REJECT면 그대로 `rev-2.md`를 만들고 재리뷰한다.
4. **빌드.** `execution.mjs set-task --root <repo> --slug <slug> --task <id> --run-status building`을 실행(직렬 B2의 ①과 같은 목적 — 이 태스크를 빌더-부트스트랩 후보로 표시)하고, baseline 캡처(`node <ROOT>/scripts/loop.mjs capture <taskWt>`) 후 **Codex 빌더**(codex MCP, `sandbox:"workspace-write"`, `approval-policy:"never"`, `cwd:<taskWt>`)에게 위임 — 모델을 선택할 수 있으면 `model-matrix.md` §3에 따른 **run 난이도 모델**(easy = `gpt-5.6-luna`, 순수 기계적이면 `gpt-5.3-codex-spark`, medium = `gpt-5.6-terra`, hard = `gpt-5.6-sol`)을 쓰고, 아니면 설치 기본값. 태스크의 manifest scope와 B2와 같은 6-section 계약을 실어주고, 추가로 **`<taskWt>/.harnie/design/rev-1.md` 경로**(또는 최신 `rev-N.md`)를 구현 前에 읽도록 지시한다 — 직렬 B2의 run-root `.harnie/plan/<slug>/`와 달리, 이 경로는 빌더 자신의 `cwd` 안에 있고 이 태스크만의 머지 前 설계(run 권위 상태가 아님)를 담고 있으므로, 빌더에게 가리켜도 같은 경계를 넘지 않는다.
5. **코드 리뷰, 머지 前 품질 게이트.** fix-delta 캡처(`node <ROOT>/scripts/loop.mjs delta <taskWt> <baselineSHA> --scope <task-scope-paths> --out <taskWt>/.harnie/review/code/delta.patch`). 리뷰어 = read-only **`harnie-reviewer`**(빌더의 프로바이더와 달라야 함). `apply`: `node <ROOT>/scripts/loop.mjs apply --root <taskWt> --ledger <taskWt>/.harnie/review/code/ledger.json --review <taskWt>/.harnie/review/code/round-N.txt --ns CR --state <taskWt>/.harnie/review/code/state.json --artifact <postSHA>`. REJECT → codex-reply가 델타만 수정 → 재리뷰, B3(`phases/phase-b.md`)와 같은 방식으로 APPROVE까지.
6. **승인된 작업을 커밋한다 — 태스크의 선언된 경로로만 스코프, 맨 `-A` 금지.** `loop.mjs`의 capture/delta는 working tree를 다룰 뿐 git history를 다루지 않으므로, 위 어디에도 커밋이 없다 — 그런데 `worktree.mjs merge`(B3′)는 브랜치를 merge하고, 그러려면 커밋이 있어야 한다. 5단계가 APPROVE에 도달하면 `<taskWt>` 안에서: `git add -A -- <태스크의 선언된 manifest scope 경로들>` 후 `git commit`. **스코프 경로로 스테이징한다, `git add -A -- . ":(exclude).harnie"`도 맨 `git add -A`도 아니다** — `.harnie/`는 gitignore 대상이 아니므로(위 노트 참조, 왜 아니면 안 되는지) 둘 다 이 태스크의 `design/rev-N.md`와 리뷰 루프 기록까지 실제 소스 변경과 나란히 스테이징해버린다(exclude pathspec도 도움이 안 된다: 일반적인 비-sanctioned `git add` 명령 텍스트에 든 리터럴 `.harnie`가 Bash 가드의 포괄적 `.harnie` 보호에 그대로 걸려 거부된다 — 5단계의 `delta`/`apply`와 달리 이 `git add` 호출은 sanctioned CLI가 아니므로 이 가드가 여전히 적용된다). 그렇게 스테이징되면 `worktree.mjs merge`가 그 `.harnie/` 내용을 run 브랜치에 커밋해 넣어 그 시점부터 run worktree의 추적 tree를 영구히 오염시킨다. 스코프 경로만 이름하면 명령에 `.harnie`가 전혀 등장하지 않으므로 가드에 걸리지 않는다. 커밋은 working tree를 바꾸지 않으므로 5단계의 `--artifact` 검사를 훼손하지 않는다.

이 태스크의 B3 확인 라운드(B3′ 4단계)를 돌리기 前에, run의 `notepad.md`에 태스크마다 항목 하나를 append한다: 그 태스크의 설계·코드 리뷰 verdict와 라운드 수. B3(`phases/phase-b.md`)의 확인 라운드가 이걸 사전 맥락으로 읽고(그 파일의 B3 병렬-경로 노트 참조), worktree가 나중에 제거되면(B3′ 5단계) 이게 태스크 리뷰의 유일한 흔적이 된다 — 기록이지, 확인 라운드의 대체물이 아니다.

**B3′. 순차 통합, 한 번에 태스크 하나씩.** B2′에서 APPROVE에 도달한 태스크부터 run 브랜치로 통합한다 — 여러 태스크가 병렬로 빌드를 마쳤어도 **한 번에 하나씩**(유일한 필수 직렬화 지점). "한 번에 하나씩"은 한 태스크의 **B3′ 전체**(1~5단계)를 뜻하지 그 merge만이 아니다: 현재 태스크의 5단계(worktree 제거)가 끝나기 前엔 다음 태스크의 1단계(baseline 캡처)를 시작하지 않는다 — 진행 중인 태스크의 미해결 상태 위에 두 번째 merge가 동시에 얹히면, 그 태스크 자신의 확인 라운드 delta가 귀속 안 된 잡음으로 오염된다.

1. **그 태스크의 merge 직전에 baseline을 캡처하고 권위를 스냅샷한다:** `loop.mjs capture <task's repo workroot>` → `mergeBaselineSHA`(workspace run: 멤버 워크루트 — run root의 `capture <repo>`는 composite `ws:` artifact를 반환하는데, delta baseline이 아니라 gate binding이다). B3 확인 라운드(4단계)가 대조할 R1 baseline이 이것이므로, 여기서 캡처해야지 더 일찍 캡처하면 안 된다(더 일찍이면 앞 태스크의 merge가 이미 들여온 것까지 포함돼 버린다). 그다음 `node <ROOT>/scripts/execution.mjs seal --root <repo> --slug <slug>`. **여기서, merge 前에 한 번만** seal한다 — 나중이 아니라. `execution.mjs`의 권위 해시는 `.harnie/plan/<slug>/` 아래 모든 `review/*/{ledger,state,receipt}.json`을 훑는데, 3단계 자체의 충돌 해결 리뷰(있다면)가 정당하게 새 파일 하나를 쓴다 — 그 뒤에 seal하면 나중의 `seal-verify`가 그 정당한 기록을 훼손으로 본다.
2. `node <ROOT>/scripts/worktree.mjs merge --repo <repo> --branch harnie/<slug>-t<id> --into harnie/<slug>`(`<repo>`의 현재 체크아웃 브랜치가 이미 `into`여야 한다 — run worktree는 항상 자기 브랜치에 있으므로 구조적으로 항상 성립). 내부적으로 `git merge --no-ff --no-edit`를 돈다. stdout은 성공 시 JSON `{ok:true, conflicts:[]}`, 충돌 시 `{ok:false, conflicts:[<경로들>], stderr}` + exit 3.
3. **권위를 확인한 뒤 merge 결과를 처리한다:**
   - **클린 merge(exit 0):** `node <ROOT>/scripts/execution.mjs seal-verify --root <repo> --slug <slug>`를 한 번 돈다. `.harnie/`는 애초에 어떤 브랜치에도 커밋된 적이 없으므로 merge가 결과와 무관하게 그걸 건드릴 수 없다 — 이 호출은 merge 자체가 아니라 이 구간에 다른 무언가가 권위를 건드렸는지 잡기 위함이다.
   - **충돌(exit 3):** merge는 미해결 상태로 남고 충돌 파일이 stdout에 나열된다. **손대기 前, 이 충돌 상태 그대로 baseline을 지금 캡처한다:** `node <ROOT>/scripts/loop.mjs capture <repo>` → `resolveBaselineSHA`. (해결 *후에* 캡처하면 해결된 tree를 자기 자신과 비교하게 돼 빈 delta가 나오고, 아무것도 리뷰하지 않은 라운드가 조용히 APPROVE된다.) 손으로 해결하고 해결 커밋을 만든 뒤 `execution.mjs seal-verify --root <repo> --slug <slug>`를 돈다 — 해결은 추적되는 소스 파일만 건드렸으니 통과해야 정상이다. 불일치면 다른 무언가가 권위를 바꾼 것이고 이 라운드는 무효다(seal-verify가 쓰이는 다른 모든 곳과 같은 판정). 통과하면 **그 델타에 대해서만 CR 라운드 1회**를 돈다: `loop.mjs delta <repo> <resolveBaselineSHA> --scope <해결이 건드린 경로> --out .../review/merge-t<id>/delta.patch` 후 `.harnie/plan/<slug>/review/merge-t<id>/` 아래 apply(B2′ 5단계와 같은 방식, run worktree에 뿌리). 이 태스크는 이 라운드가 APPROVE되기 전엔 4단계로 넘어가지 않는다(위 헤더에 따라 다음 태스크의 B3′도 마찬가지). **해결이 이미 merge·확인된 앞선 태스크의 선언된 `scope`** 안쪽 경로를 건드렸다면(이 태스크의 것만이 아니라), 그 앞선 태스크의 B4 receipt는 이제 stale이다 — 계속하기 前에 그 태스크의 B3 확인(새 baseline을 지금 캡처, 그 앞선 태스크의 선언된 `scope`로 delta 범위 지정, 그 기존 `<dir>`에 리뷰·apply)과 B4 verify를 현재 tree에 대고 재실행한다. 뒤 태스크만 반려·rebase하는 것으로는 앞선 태스크의 바인딩이 고쳐지지 않는다.
   어느 쪽이든, 아래 4단계의 B3 확인 라운드 서두에서 `seal`/`seal-verify`를 반복하지 않는다 — 이 쌍이 이미 그 전제조건을 충족했다(`phases/phase-b.md`의 B3 병렬-경로 노트 참조).
4. **이 태스크의 B3 확인 라운드(`phases/phase-b.md`)를 run worktree에서** 1단계의 `mergeBaselineSHA`부터 현재 tree까지 — 즉 merge와 (있었다면) 3단계의 충돌 해결 커밋까지 포함해서 — 돌린다. 태스크 worktree를 제거하기(5단계) **前에** 한다: REJECT되면 아직 존재하는 태스크 worktree와 아직 등록된 빌더 스레드로 수정이 돌아간다(`phases/phase-b.md`의 B3 병렬-경로 노트 참조 — `codex-reply`·커밋·재-merge·재리뷰). 이 라운드가 APPROVE된 후에만 5단계로 진행한다.
5. `node <ROOT>/scripts/worktree.mjs remove --repo <repo> --branch harnie/<slug>-t<id> --archive-to <repo>` — 태스크의 `.harnie/review/`를 run의 `.harnie/plan/<slug>/review-archive/t<id>/`로 옮긴(validated against active sentinel, manifest task, repo registration; 재실행에 멱등) 뒤 worktree를 제거한다. archive가 태스크 unit 리뷰의 durable record — `harness-digest`가 이를 읽고, confirmation 라운드의 "prior verdict/rounds" context가 이를 가리킨다. 이 경로에선 항상 `--archive-to`로 제거한다.

## Design-defect corrections during execution (errata v2 propagation)

Runner가 `errata-candidate`를 보고하거나 당신이 승인된-설계 결함을 관찰하면, `phases/phase-b.md`의 Design errata section을 따른다: `errata-add`, blocker/degrade는 사용자 approval 받기(`errata-arm` + AskUserQuestion). 정정 승인 후 brief의 cited-sections 헤더로 전파:

- **Affected set** = 정정된 섹션을 cite한 태스크들 + 그들의 transitive manifest `deps` descendants.
- *Unstarted:* brief를 `t<id>-brief.v<N+1>.md`로 reissue(새 파일, 절대 overwrite) — spawn 前.
- *Runner in flight:* TaskStop, brief reissue, respawn — resume table과 bound thread가 이를 safe하게 함.
- *Built, unmerged:* fresh `capture --record` baseline → `codex-reply`로 태스크 worktree에 정정 주입 → 그 baseline에서 delta 리뷰.
- *Already integrated(worktree 제거됨):* `execution.mjs rebind-task --root <repo> --slug <slug> --task <id> --reason correction:<E-NNN>` — audit-log 스레드 release, `pendingRunRootBootstrap` marker arm(한 번에 하나) — 그 다음 serial-path fix 라운드(run worktree, scope = 그 태스크의 manifest scope; baseline을 그 태스크의 reviewUnit 아래 `--record`로 캡처 — bootstrap call 前). Engine이 새 스레드를 marker의 태스크에만, cwd git root가 그 태스크의 repo workroot와 일치할 때만 bind. Disk가 이미 필요한 수정을 가졌고 리뷰가 approval 없이 APPROVE되면, marker를 `rebind-task --cancel --task <id> --reason approved-artifact:<postSHA>`로 close. 전체-tree 변경은 이미 APPROVE된 Final Wave gate들을 무효화; completion은 그들의 재실행을 강제.
- *Descendants(deps closure):* 정정된 ancestor의 fix merge 후 그들의 B4 verify 재실행; descendant의 verify fail이면 fix target으로 escalate만.

**Correction-round resume (marker states — `execution.json` + run tree에서 판정, 모두 당신이 실행):**

| Observed | Re-enter |
|---|---|
| marker pending · task unbound · tree clean | bootstrap codex call 재발급(marker는 bind 성공까지 designating 유지) |
| marker pending · unbound · tree dirty (disk에 partial fix) | recorded baseline에서 delta → disk 상태를 producer 산출로 리뷰; REJECT → partial fix를 프롬프트에서 명시해 re-bootstrap; **APPROVE → marker close: `execution.mjs rebind-task --root <repo> --slug <slug> --cancel --task <id> --reason approved-artifact:<postSHA>`**, 그 다음 confirmation + verify |
| marker cleared · bound · dirty (fix 도중 죽음) | normal REVISING resume via bound thread에 `codex-reply` |
| marker pending · bound | impossible (bind+clear is atomic) — STOP and report state corruption |
