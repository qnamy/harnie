# dev-solo — the harnie Pipeline, Codex-Standalone

You are Codex running harnie's single pipeline **without Claude subagents or hooks**. Same stages, same hard rules as `harnie:dev`; only the wiring differs. `<SNAP>` = this plugin's install root (the marketplace snapshot — resolve it once from this file's own location). All state CLIs are `node <SNAP>/scripts/execution.mjs|loop.mjs …`.

## Wiring differences (everything else follows the harnie:dev contract — Read `<SNAP>/skills/dev/SKILL.md` now)

- **Init (no bootstrap hook)**: `execution.mjs init --root <repo> --slug <slug> --authority cli` — creates the run state in that repo root; use the repo root everywhere. Then judge provisional size/difficulty; confirm size with `set-mode` (upward-only) and difficulty at the two re-judgment checkpoints (`model-matrix.md` §2) with `set-difficulty`.
- **Resume or runtime handoff**: do not call `init` for an existing run. Run `execution.mjs runs --root <repo>`, present the returned `blockers[]`, then run `execution.mjs handoff --root <repo> --slug <slug>` for the selected run before continuing from its next incomplete stage.
- **Approval (M)**: present `plan.md` to the user in conversation; after their explicit approval run `execution.mjs approve --root <repo> --slug <slug> --plan-hash <hash>` (hash mismatch fails). The approve call, hash, and time are the audit record.
- **Producer = you.** Write designs and code yourself (no builder delegation). Everything the builder contract forbids still binds you: scope tests only, no unrequested work, evidence-backed completion (`<SNAP>/instructions/builder-contract.md`).
- **Reviewer = a native Codex subagent with `fork_turns: "none"` (the only review path — not a fallback)**: spawn it with `task_name`, the review prompt as `message`, `fork_turns: "none"`, and `model` = the T3 Codex model resolved from `model-matrix.md` §3 (`reasoning_effort: "high"` only at `very-hard`). Used for both design reviews (any altitude) and code reviews. **`fork_turns: "none"` is the contract, not a default** — omitting it copies your conversation into the reviewer and destroys the isolation this path exists for. The prompt names the criteria file paths (`<SNAP>/instructions/code-review.md` or `design-review.md` with the altitude, `verification-tiers.md`, `review-schema.md`) and demands the exact review-schema output. For each review artifact and prior ledger inside the run, give the repo root plus its `.harnie/`-relative path and instruct the subagent to read it from stdout with `node <SNAP>/scripts/loop.mjs export <repo> <rel>` **without `--out`**. The trusted CLI reads the artifact without putting `.harnie` in the Bash command or creating a staging copy. The subagent's final answer comes back to you as a string; save it as `<dir>/round-N.txt` with the Write tool. If the spawn fails, stop and report — there is no other fallback.
  - **The reviewer's read-only property is an instruction, not a mechanism** (0.14.5). The previous path was `codex exec --sandbox read-only`, where the OS blocked writes. A native subagent inherits the parent's sandbox and there is no per-spawn sandbox argument, so a reviewer that decides to write can. State "read only; never modify any file" in the review prompt and treat a reviewer that writes as a protocol failure to report, not something the harness will catch. `docs/enforcement-map.md` records this as advisory. Why the trade was taken: the subprocess path cannot start at all inside a sandboxed session (`failed to initialize in-process app-server client`), so it made unattended Codex runs impossible and forced a per-round approval prompt in interactive ones; it also forced run artifacts to be copied outside `.harnie` because the prompt rode on a command line the Bash guard blanket-denies. The subagent path removes the nested process, per-round approval, and staging copy; the trusted `export` stdout read remains because native subagents have no separate filesystem Read tool.
  - Save the subagent's returned answer as `<dir>/round-N.txt`, then `loop.mjs apply …` exactly per `review-loop-driver.md` R4 (CR artifacts from `loop.mjs capture/delta`; DR artifacts as `dr:` hashes). A schema-invalid response (`needsReRequest`) gets one re-request; if it is still invalid, **stop and report the protocol failure to the user** — `apply` records no state on invalid rounds, so this is not a STALLED latch and `--reentry` does not apply.
- **Why self-review, not cross-model**: dev-solo exists so development can continue Codex-standalone when Claude usage/tokens are exhausted — that is its entire reason to exist. In that scenario a cross-model reviewer is unavailable by construction, so self-review is inherent to this mode, not a degraded fallback — an accepted, documented tradeoff (narrower blind-spot coverage than `harnie:dev`'s cross-provider loop).
- **Verification/completion**: `verify --task`, `verify --integration`, and `completion` as in harnie:dev; `completion` is the only source of the `HARNIE_STATUS` footer. Run `seal`/`seal-verify` around each producer window even though you are the producer — it catches accidental authority-file edits.
- **Larger than M**: the same handoff rule as `harnie:dev` — stop and report that the job belongs to the human + orca process; there is no L pipeline to run.

## NEVER (beyond harnie:dev's list)

- Approve, close review IDs, or emit HARNIE_STATUS from your own judgment — only the CLIs.
- Review your own work in this conversation's context — the reviewer is always a subagent spawned with `fork_turns: "none"`.
- Spawn the reviewer without `fork_turns: "none"`, or fall back to `codex exec` / an MCP server for the review path; the native-subagent route above is the whole contract.
- Call the `claude` CLI — dev-solo's reviewer is Codex-only (see rationale above); there is no cross-model fallback to reach for.
