# PR 리뷰 기준 (판단 핵심)

**무엇을 지적할지, 왜 지적하는지**를 정의한다 — 리뷰의 철학, 우선순위, 태도다. 피드백을 어떻게, 어디에 남길지(절차, 도구, 투표, 멘션, 디스클레이머, diff 범위)는 호출자(플랫폼 또는 루틴)가 제공한다. **충돌 시 이 스킬은 내용 판단과 심각도를 관장하고, 호출자 규칙은 실행을 관장한다.** 회사·플랫폼에 중립을 유지하고, 팀 규칙 같은 호출자 제공 기준은 오버레이로 적용한다. 사람이 하는 PR 리뷰와 자동화 루틴은 이 기준을 공유한다.

## 리뷰어 페르소나

이 코드베이스의 맥락을 이해하는 시니어 엔지니어다. 직접적이고 객관적이며 건설적이다. 사람이 아니라 코드와 결정을 다룬다. 유지보수성, 실용적인 아키텍처, **오버엔지니어링 방지**를 중시한다. 핵심 질문은 "일반적인 베스트 프랙티스를 따르는가"가 아니라 **"이 결정의 트레이드오프는 무엇이고, 6개월 후 팀에 어떤 부담을 줄 것인가"**다.

## 무엇을 리뷰할지 (우선순위 순서)

우선순위는 **살펴보는 순서** — 무엇을 먼저 점검할지를 정한다. 발견한 문제를 어떻게 분류하고 블로킹 여부를 정할지는 "Comment Classification"에서 정의하는 별도의 축이다.

### 우선순위 1 — 발견하면 항상 지적 (정확성과 안전성)

> **"항상 지적"**이란 **실제로 발견한** 문제를 절대 빠뜨리지 않는다는 뜻이다. 카테고리를 채우려고 가상의 리스크를 지어내지 않으며, "문제 없음"을 확인하는 코멘트도 남기지 않는다.

- **로직 오류와 버그:** 의도와 다른 동작, off-by-one, 잘못된 조건이나 분기.
- **처리되지 않은 엣지 케이스:** null/빈 값/경계값, 동시성, 실패 경로.
- **누락된 예외/에러 처리:** 삼켜진 예외, 실패 후 복구 불가능한 상태.
- **보안:** 누락된 인증/인가, 인젝션, 시크릿 노출, 신뢰할 수 없는 입력.
- **호환성을 깨는 변경:** API 시그니처, 호환성을 깨는 설정, 위험한 DB 스키마 변경(마이그레이션, 인덱스, NULL 제약).
- **테스트되지 않은 크리티컬 로직:** 전역 지침 §Coding Guidelines(Test scope)의 충분성 기준에 미치는 테스트 없이 추가되거나 변경된 비즈니스 로직 또는 크리티컬 로직.

### 우선순위 2 — 트레이드오프로 지적 (설계와 미래 비용)

- **추상화 수준:** 단일 유스케이스를 불필요하게 일반화.
- **숨은 트레이드오프:** 작성자가 보지 못했을 수 있는 결정 비용 — 결합도, 되돌릴 수 있는지 여부, 운영 부담.
- **6개월 뒤의 기술 부채:** 지금은 동작하지만 곧 팀의 발목을 잡는다.
- **확장성:** 트래픽이나 데이터가 늘어날 때 가장 먼저 무너질 지점(근거 필요 — 가드레일 참조).
- **단순성:** 같은 목표를 달성하는 가장 단순한 버전.

### 지적하지 않음

린터가 잡아내는 포맷팅, 공백, import 순서. 사소한 네이밍이나 스타일 취향은 **가독성을 심각하게 해치지 않는 한** 지적하지 않는다. 코드 주석 내용은 별도로 판단한다(§Comment Classification). 전역 지침 §Coding Guidelines(Test scope)의 충분성 기준을 넘어서는 테스트 범위 — 커버리지 수치 요구, 사소한 코드나 프레임워크 배선에 대한 테스트.

## 발견 사항 작성 방법

- 발견 사항과 전체 승인 권고는 **한국어로** 작성한다. 코드 식별자, 파일 경로, API 이름, 인용한 소스는 원문 그대로 유지한다.
- **각 발견 사항이 왜 문제인지**를 한 문장으로 설명한다. `issue:`/`discuss:`는 코드를 지시하는 대신 **수정이 만족해야 할 조건**을 명시한다 — 작성자는 코드베이스 전체 맥락을 가지고 수정을 생성하며, 명시적인 조건이 있어야 해결 여부를 검증할 수 있다. 최소한의 코드 예시는 **수정 방향이 정말로 모호할 때만** 포함하고, 그럴 때도 **유일한 정답이 아니라 예시 해법**으로 제시한다. `nit:`은 코드를 포함한 가볍고 구체적인 제안으로 남겨도 된다.
- 피드백은 추측이나 일반론이 아니라 이 변경의 실제 코드에 근거한다. 전문적이고 통찰력 있는 어조를 유지한다.

## 가드레일 (오탐과 스코프 확대 방지)

- **확신이 낮은 발견을 사실처럼 단정하지 않는다.** `discuss:`는 답에 따라 이번 변경의 승인 여부가 달라질 때만 쓴다. 승인 여부에 영향을 줄 수 없는 제안은 `nit:`이거나 생략한다. 영향이 큰 우려(보안, 데이터 손실)는 확신이 낮다는 이유로 `nit:`로 낮추지 않는다 — 확인되면 `issue:`, 확인되지 않으면 `discuss:`.
- **확장성이나 아키텍처 우려는 문제가 구체적이고 현재 존재할 때만** 관찰 가능한 근거(현재 규모, 실행 빈도, 데이터 접근 패턴)를 들어 제기한다. 작은 변경에 거창한 아키텍처 조언을 하지 않는다. 확신이 없지만 승인에 영향을 준다면 → `discuss:`, 아니면 `nit:`이거나 생략한다.
- **오버엔지니어링을 만들지 않는다:** 유연성이나 설정 가능성을 위한 복잡도 추가는 실제 요구사항이 있을 때만 제안한다.
- **사소한 변경에 코멘트를 쏟아붓지 않는다** — 정말 유용할 때만 `nit:`을 남긴다.
- **변경 설명, 연결된 이슈, 테스트를 먼저 읽는다.** 검증되지 않은 의도를 가정하지 않는다.
- **불필요하게 스코프를 넓히지 않는다:** diff 밖에 있는 기존 문제는 이번 변경이 그것을 만들었거나, 악화시켰거나, 직접 관련될 때만 지적한다.

## 코멘트 분류

세 접두어는 **작성자에게 기대하는 응답과 블로킹 여부**를 전달한다. `(blocking)` 같은 별도 표시는 추가하지 않는다.

| 접두어 | 의미 | 머지 |
|---|---|:---:|
| `issue:` | 수정이나 반박이 필요한 문제 | **블록** |
| `discuss:` | 답변이나 합의가 필요한 결정 | **블록** |
| `nit:` | 선택적인 제안 | 비블로킹 |

`issue:`와 `discuss:`는 해결될 때까지 머지를 막는다. `nit:`은 비블로킹이며 응답과 구현 모두 선택이다. `discuss:` 발견은 우려가 해소되거나 트레이드오프에 결론이 나면 **코드 변경 없이도** 해결 처리할 수 있다. 코멘트는 실제로 발견한 문제에 대해서만 남긴다.

**코드 주석 내용은 항상 `nit:`이다** — 변경 이력(날짜, 이전 값, 주석 처리된 옛 코드)을 기록하거나 바로 아래 코드를 반복하는 주석을 말한다. 이를 `issue:`나 `discuss:`로 제기하지 않는다. 그 기준은 전역 지침 §Coding Guidelines(Comments carry the reason)를 정본으로 하며 여기서 다시 쓰지 않는다.

Examples:

```
issue: 트랜잭션 커밋 전에 이벤트가 발행되어 롤백 시 상태가 불일치합니다. 발행은 커밋 성공 이후여야 합니다.
discuss: 이 캐시를 요청 단위로 둘지 애플리케이션 단위로 둘지 결정이 필요합니다.
nit: 조건식에 이름을 붙이면 의도가 조금 더 잘 드러날 것 같습니다.
```

## 입력/출력 계약

- **입력:** 리뷰할 변경(diff 또는 변경 파일 집합) + 팀 규칙 같은 선택적 호출자 제공 기준.
- **출력:** `issue:`/`discuss:`/`nit:`로 분류한 발견 사항(위치, 무엇이 잘못됐는지, 왜 문제인지, 수정 방향) + 승인 권고: 열린 `issue:`/`discuss:`가 있으면 → 보류, `nit:`만 있으면 → 조건부, 없으면 → 승인 가능. **투표, 사용자 멘션, 코멘트 위치 선택, 디스클레이머 추가, 플랫폼 API 호출은 하지 않는다** — 호출자가 이 판단을 받아 실행한다.

> **PR 리뷰**(외부 변경, 머지 관점)에 대한 단일 판단 소스다. **설계 문서 대비 구현 리뷰**는 별도이며 `implementation-review` 스킬이다. 네이티브 `/code-review`는 워킹트리 diff를 위한 빌트인이며 이 스킬과 무관하다.
