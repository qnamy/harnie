# L 단계 — 태스크 분할, 러너, 통합, 최종 리뷰

> 규모가 L로 확정되면 `SKILL.md`에서 읽는다. SKILL.md의 모든 것(MUST/NEVER, 승인 게이트, 컨테스트, 컨텍스트 예산)이 그대로 적용되며, 이 파일은 L 전용 시퀀스만 추가한다. 워크스페이스 run(멀티레포 진입)은 0.10 규칙을 유지한다: 승인 전에 각 레포를 `execution.mjs repo-add`로 등록하고, 모든 태스크와 `integrationVerification` 항목이 `repo` 키를 가지며, 태스크별 git 작업은 해당 멤버 workroot를 사용한다.

## 시퀀스

1. **ARCH 설계 + 리뷰 (ARCH 트리거가 성립할 때만)** — 트리거: ① 신규 컴포넌트/모듈/서비스 ② 경계 또는 모듈/레포 간 계약 변경 ③ 데이터 소유권 또는 스토리지 선택 ④ 기술 선택 ⑤ SPOF/스케일링/가용성 결정. 프로듀서 = `harnie-designer`(opus — hard는 effort high; very-hard는 `fable`·폴백 opus+effort-high; `model-matrix.md` §3의 ARCH 행 기준; 프로파일 경로 `design-authoring-arch.md`, formal)가 `design/arch-rev-N.md`(리비전마다 새 파일)를 작성; 리뷰어 = **ARCH 고도**의 Codex, DR 루프 사용(`review/design-arch/`, 아티팩트 `dr:` 해시). 근거 없는 공식 아키텍처 단계는 스코프 인플레이션이다 — 기존 아키텍처가 유효하면 생략한다.
2. **태스크 분할 초안 → 태스크 스코프 그라운딩 → CONTRACT.** 분해 초안을 작성한 뒤, 초안 태스크별로 `harnie-scout`를 병렬 스폰해 해당 코드 경로, 기존 테스트, 런타임/드라이버·세션 시맨틱스를 검증한다 — 태스크별 환경 팩트 시트다. 프로듀서 = `harnie-designer`(프로파일 `design-authoring-contract.md`)가 **그 증거 위에서** `design/contract-rev-N.md`를 작성한다: 분해 테이블(태스크별 독립-리뷰-가치 근거 — 기본 병합 규칙은 프로파일에 있다), 태스크 간 계약, 팩트 시트, 검증 전략(자동/사람). 리뷰어 = **CONTRACT 고도**의 Codex(`review/design-contract/`).
3. **승인 (1회)** — `plan.md` = CONTRACT 요약 + 매니페스트 블록(`gates: [final-review]`, `integrationVerification` 필수); SKILL.md의 승인 게이트 규칙이 적용된다(증거 증명, arm → 원샷 AskUserQuestion).
4. **브리프** — 태스크별 `tasks/t<id>-brief.md`: 매니페스트 항목 + 해당 태스크의 분해 행, 관련 계약 섹션, 팩트 시트(발췌) + notepad 발췌 + `builder-contract.md` 경로. 승인된 교정이 인용된 섹션을 건드리면 `.vN+1`(새 파일)로 재발행한다.
5. **실행 웨이브 — 모든 태스크가 확정될 때까지 5→6을 반복한다.** 각 웨이브: deps가 **모두 확정된**(6단계 완료 — 단순 병합이 아니라) 모든 태스크에 대해: `set-task … building` 후 `harnie-task-runner`를 스폰한다(백그라운드; 모델 오버라이드로 유닛-리뷰 티어) — 태스크 id, run workroot, 태스크 레포 workroot, `<ROOT>`, 브리프 경로, 빌더 모델, 그리고 — respawn 시 — 바인딩된 `builderThreadId`를 전달한다. 설치본에서 러너 경로 최초 실행이면: 단일 카나리아 러너 먼저(바인딩 핸드셰이크). 종료 보고를 `notepad.md`에 수집하고 FAILURE를 분류한다(인프라 fail-fast → 스폰 중단, 알림, 세션 재시작 권고; 워치독 거부 → 태스크당 1회 `watchdog-extend --reason auto-cap`으로 자체 연장, 상한 초과는 사용자에게 질문; STALLED → 표면화 후 `--reentry`; `contract-conflict:` → 7단계). 새로 자격을 얻은 종속 태스크는 다음 웨이브에 들어간다.
6. **순차 통합, 한 번에 태스크 하나** — 태스크의 멤버 workroot에서 `mergeBaselineSHA` 캡처, `seal`, `worktree.mjs merge`; 충돌 시: capture-before-touch, 해소, 해소 델타에 CR 1라운드. 이어서 **확인 라운드**(`harnie-reviewer`, confirmation 티어, mergeBaselineSHA 기준 델타, 이전 유닛 판정을 컨텍스트로 — REJECT 시 태스크의 아직 살아 있는 worktree와 바인딩된 스레드로 수정하고, 증분 재병합 후 재리뷰)와 그 태스크의 `verify --task <id>`. **확인 APPROVE + verify 통과 후에만** `worktree.mjs remove … --archive-to <repo>`로 worktree를 제거한다 — 항상 아카이브하고, 절대 그보다 먼저 제거하지 않는다. 한 태스크의 통합을 전부 마친 뒤 다음으로 넘어간다(seal은 run 스코프다).
7. **진행 중 CONTRACT 결함 (errata 경로)** — 결함은 누구든 표면화할 수 있지만, 등록은 오직 당신이 한다: `execution.mjs errata-add --root <repo> --slug <slug> --severity <blocker|degrade|note> --design-ref "contract-rev-N §…" --defect "<what+evidence>"`. `note` → `errata-set-disposition --root <repo> --slug <slug> --id E-NNN --disposition <value> --correction <text|@file>`(CLI 전용); `blocker`/`degrade` → 결함 있는 진술에 기대는 빌드를 멈춘 뒤, `errata-arm --root <repo> --slug <slug> --id E-NNN --disposition <approved-workaround|deferred-next-run|superseded-by-A5.2> --correction <text|@file> --approve-option "<label>"` + 바로 다음 AskUserQuestion(원샷 바인딩; 정확 일치). 승인되면 인용 섹션 기준으로 전파한다: **미착수** 태스크 → 스폰 전에 브리프 `.vN+1` 재발행; **비행 중 러너** → TaskStop, 재발행, respawn(재개 안전); **이미 통합됨** → `rebind-task --task <id> --reason correction:E-NNN`(run-루트 부트스트랩 마커를 arm)과 run 루트에서 직렬 수정 라운드, 또는 디스크가 이미 충족하면 `--cancel --reason approved-artifact:<postSHA>`; **deps 하위 태스크는 `verify`만 재실행하며, 실패 시에만 수정 대상으로 격상한다**. 재발행된 브리프는 태스크의 설계 승인을 기계적으로 무효화한다(`dr:` 불일치). 스코프/검증/태스크를 건드리는 것은 무엇이든 `superseded-by-A5.2` — 전체 매니페스트 재승인이다; errata는 계약 산문만 교정한다. 미결 blocker/degrade 항목은 완료 차단 요소로 계산된다.
7b. **통합 후 코드 수정**(worktree 제거 후의 확인 REJECT, 통합 검증 실패, Final Review 파인딩): `rebind-task --root <repo> --slug <slug> --task <owning id> --reason <correction:E-NNN | finding:<reviewUnit>:CR-NNN | verification:integration>` — 계약 결함에서 비롯되면 `correction:`(먼저 errata를 등록); 순수 코드 결함이면 `finding:`으로 **그것을 제기한 ledger의 리뷰 유닛과 해당 CR ID**를 명명한다(유닛 스코프 — CR ID는 ledger 간에 반복된다); 통합 검증 자체가 실패했으면 `verification:integration`(거기엔 ledger가 없다) → 그 태스크의 reviewUnit 디렉터리에 기록형(recorded) 베이스라인 캡처 → run 루트에서 부트스트랩 빌더 호출 1회(마커가 이를 바인딩) → 델타에 CR 라운드 → `verify --task` 재실행, 이어 `verify --integration`(기존 영수증은 트리-무효화됨), Final Review가 이미 승인했었다면 재실행.
8. **통합 검증** — 모든 태스크가 확정된 후: `verify --integration`(전체 스위트; 최종 트리에 바인딩된 통과 영수증 1개; 실패 → 소유 태스크의 스레드로 수정 → 재실행).
9. **최종 리뷰 (유닛 1개)** — 리뷰어 = **opus**의 `harnie-reviewer`, 유닛 `review/final-review/`, 전체 트리 아티팩트(워크스페이스 run에서는 `ws:` 합성). 4-렌즈 체크리스트를 한 패스로: coverage(모든 플랜 요구사항이 구현됨), quality(전체 `code-review.md`), runtime(통합 영수증을 통한 증거 — **테스트 재실행 금지**), scope(요청되지 않은 것 없음). 승인 후 트리 변경은 이를 기계적으로 무효화한다.
10. **완료** — `execution.mjs completion`; 태스크별 판정/라운드, 통합 영수증, 최종 리뷰 판정, 사람 검증 체크리스트, errata 다이제스트를 보고; `HARNIE_STATUS` 푸터로 끝낸다.

## L 전용 NEVER

- 독립 리뷰 가치에 못 미치는 태스크를 매니페스트에 두지 않는다(병합한다 — 게이트가 근거 컬럼을 사용자에게 보여준다).
- "전체 재검증" 태스크, 또는 8단계 밖의 전체 스위트 실행 일체.
- 의존성의 **확정**(단순 병합이 아니라)이 승인되기 전에 종속 태스크를 시작하지 않는다.
- `notepad.md`에 근거 기록 없이 disjoint 태스크 ≥2개를 직렬 실행하지 않는다.
