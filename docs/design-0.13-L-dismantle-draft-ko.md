## 1. Executive Summary

**권고: 부분 해체 — "L의 실행 계층"만 해체하고, 설계 계층과 통합 계층은 존치한다. 그리고 그 해체의 0.13 구현은 신규 메커니즘 0개짜리 "조립 가이드"로 한다(Option 1).**

세 가지가 이 결론을 끌었다.

1. **경계는 취향이 아니라 훅 소유권이 정한다.** harnie의 기계 강제(빌더 스레드 귀속·승인 바인딩·seal·완료 유도)는 전부 `run sentinel의 owner session`에 걸려 있다(§3-F4). 실행을 소유 세션 밖으로 내보내는 순간 그 실행에는 강제가 **하나도** 걸리지 않는다 — 단, 그 실행이 **자기 run을 부트스트랩하면** 전부 그대로 걸린다. 따라서 "native 병렬 실행 + 중앙 harnie ledger"라는 중간 형태는 성립하지 않는다. 성립하는 유일한 형태는 **병렬 단위 1개 = harnie run 1개**다.
2. **그 형태에서 L 전용 기계는 대부분 존재 이유를 잃는다.** 태스크 러너·브리프·wave 스케줄링·errata v2 in-flight 전파는 모두 "중앙에 얼어붙은 매니페스트 아래에서 러너 N개가 동시에 도는 상태"를 관리하기 위한 장치다. 단위가 각자 독립 run이면 그 상태 자체가 없다. 특히 **errata v2는 매니페스트가 실행 중 얼어 있다는 사실 하나 때문에 존재한다** — 얼어붙은 중앙 매니페스트가 사라지면 errata의 존재 근거가 통째로 증발한다(§6).
3. **그렇다고 곧바로 새 기계를 만드는 것은 harnie 자신의 규칙 위반이다.** 조립 형태(mode `U`·dispatch 해시 바인딩·`export-completion`)는 매력적이지만 **한 번도 실행된 적 없는 형태를 위해 새 메커니즘을 미리 짓는 것**이고, 이는 harnie의 contest 게이트가 `overengineering`으로 기각할 바로 그 패턴이다. 0.13은 기존 동사만으로 손으로 조립하는 절차를 문서화하고, 실측 2회 이후에 기계화 여부를 판단한다.

**해체에 반대하는 가장 강한 논거는 U-4다** — L 러너 경로는 **어떤 버전에서도 한 번도 E2E로 돌아본 적이 없다**(§3-F1). 실측 없이 만든 계층을 실측 없이 해체하면 "미측정을 미측정으로 교체"하는 것이다. 이 반론이 결론을 뒤집지 못하는 유일한 이유는 **비대칭성**이다: 조립 형태는 **이미 실행 이력이 있는 M 경로**를 n번 재사용하는 반면, L은 **한 번도 실행되지 않은 부품**으로 조립돼 있다. 검증된 부품의 재조합이 미검증 부품의 유지보다 분산이 낮다. 그러나 이 비대칭성은 "해체해도 안전하다"를 뜻하지 않고 **"삭제를 미뤄도 비용이 거의 없다"**를 뜻한다 — 그래서 권고안은 삭제가 아니라 **동결(라우팅 차단) + deprecated 표기**다.

## 3. 사실 근거 (측정된 것 / 측정되지 않은 것을 구분한다)

### F1. L 러너 경로는 실행 이력이 0이다 — 이것이 이 검토의 출발점

- `design-0.11-process.md` §2 NFR-4②는 배포 게이트로 **L 경로 E2E 1건**을 요구하고 **[미결정 U-4]**로 남겨 두었다. `design-0.11-detail.md` §10도 통과 조건만 나열한 채 대상 미선정이다.
- 0.11의 근거가 된 fcl-hmm 런은 **0.10 버전**이고, 그 런조차 **전 구간 serial(공유 워크트리)** 로 수행됐다(`design-0.10-restructure.md` §11.6 — "15태스크 중 disjoint-scope 유닛 다수인데 직렬 경로 사용, 근거 미기록"). 즉 **러너 병렬 경로는 0.10에서도 가동되지 않았다.**
- **따라서 판정**: 0.11 L의 설계 근거는 실측이지만(hmm의 라운드·토큰·사고 기록), **L이 제안한 해법 자체는 어느 버전에서도 실행된 적이 없다.** 0.11이 스스로 "S 카나리아만으로는 배포 불가"라고 쓴 게이트가 미충족인 채 0.11.1이 배포되어 있다.

### F2. L 전용 표면의 크기 (제거 시 회수량의 상한)

| 대상 | 규모 | L 전용인가 |
|---|---|---|
| `skills/dev/stages/large.md` (+`-ko`) | 7.5KB + 8.5KB | **예** |
| `agents/harnie-task-runner.md` (+`-ko`) | 6.0KB + 7.1KB | **예** |
| `instructions/design-authoring-contract.md` (+`-ko`) | 2.5KB + 2.6KB | **예**(CONTRACT 고도는 L에만 존재) |
| `execution.mjs` errata v2 (`errata-add/arm/set-disposition/list` + completion 산입) | 참조 ~53개소 | **예** |
| `execution.mjs` 워크스페이스(멀티레포: `repo-add`·`memberWorkroots`·`ws:` 합성) | 92개소 중 일부 | **예**(단 §6에서 "이전"으로 판정) |
| `worktree.mjs merge` / `remove --archive-to` | ~110줄 | **예** |
| `verify --integration`, `gates: [final-review]` | — | **아니오** — M도 `integrationVerification` 필수 |
| watchdog · `rebind-arm` · seal · `capture --record` · ledger | — | **아니오** — S/M도 사용(`set-mode S`가 암묵 태스크 `t1`을 `building`으로 등록) |

**판정**: "L을 지우면 엔진이 절반으로 준다"는 서사는 사실이 아니다. 회수되는 것은 **문서 ~34KB + errata v2 + 워크트리 병합/아카이브 + 워크스페이스 모드**이고, 사고 유래 강제장치의 대부분(seal·watchdog·ledger·receipt·승인 바인딩)은 S/M이 그대로 쓰므로 남는다. 0.13 백로그 #2(엔진 관료제 감량)는 **이 해체와 별개의 작업**이며, 순서는 해체 → 감량이 맞다(감량의 분모가 바뀌므로).

### F3. native가 실제로 제공하는 것 (이 세션에서 확인 가능한 표면 기준)

- **`Agent` 도구**: 백그라운드 서브에이전트, `isolation: "worktree"`(에이전트별 격리 워크트리, 미변경 시 자동 정리), `SendMessage`로 컨텍스트 유지 재개.
- **`Workflow` 도구**: 결정적 JS 오케스트레이션(`parallel`/`pipeline`), 에이전트별 `isolation:'worktree'`, `resumeFromRunId`로 변경되지 않은 prefix 캐시 재사용, `journal.jsonl` 감사, 동시성 상한 `min(16, CPU-2)`, **세션에 연결된 MCP 도구를 `ToolSearch`로 접근 가능**(즉 Codex MCP 도달 가능 — 단 대화형 세션에 한함).
- **독립 병렬 세션**: 각자 자기 컨텍스트·자기 훅·자기 run.

**native가 제공하지 않는 것**: 크로스모델 강제, ledger fail-closed, 승인 원샷 바인딩, 검증 receipt·vacuous 검출, 완료 유도(정직 보고). 이것이 harnie가 남는 이유다.

### F4. 훅 소유권 — 경계를 강제하는 결정적 사실 (코드 확인)

1. `hooks/lib.mjs:93 resolveRoot(cwd, sessionId)` = `findRoot(cwd)`(상향으로 `.harnie/active.json` 또는 `.git`) → 그 root의 `.harnie/sessions/<sid>.json` 바인딩. **태스크 워크트리는 `.git`은 있지만 `active.json`이 없다** → 그 워크트리를 cwd로 하는 세션은 root를 그 워크트리로 잡고 `ctx.active === false` → **모든 가드가 무력**하다.
2. `hooks/lib.mjs:112 isOwnerSession()` — `posttooluse.mjs`의 모든 바인딩(빌더 threadId 귀속, 승인 바인딩, errata/rebind 바인딩)이 `sentinel.sessionIds` 멤버십을 통과해야 실행된다. owner 멤버십은 **`bootstrapRun`의 resume 경로로만 증가**한다(`execution.mjs:648`).
3. **따라서**: 실행을 소유 세션 밖(다른 세션·다른 워크트리)으로 내보내면 harnie의 기계 강제는 **전부 no-op**이 된다. 예외는 단 하나 — **그 실행이 스스로 부트스트랩해 자기 sentinel과 자기 owner session을 갖는 경우**. 그때는 S/M 경로의 강제가 **그대로 전부** 걸린다.
4. `bootstrapRun`은 같은 root에 미완료 run이 있으면 새 run을 거부하고, 에러 메시지가 이미 해법을 지시한다: *"별도 worktree checkout에서 이 스킬을 다시 실행해 새 run을 시작하세요."* → **n개 병렬 run = n개 별도 체크아웃**은 이미 엔진이 상정한 형태다.

> 이 F4가 이 문서의 설계 결정 대부분을 강제한다. "중앙 ledger + native 실행"은 **선택지가 아니라 불가능**이고, "단위마다 자기 run"은 **선택지가 아니라 유일해**다.

### F5. 헤드리스는 병렬 실행 단위가 될 수 없다

`claude -p`는 MCP 서버를 로드하지 않는다(훅은 정상 발화). Codex 빌더는 MCP 도구다 → **헤드리스 단위 run은 빌드를 수행할 수 없다.** 병렬 실행 단위는 (a) 사용자가 여는 대화형 세션, 또는 (b) 세션 내 `Agent`/`Workflow` 에이전트뿐이다. "무인 L 자동 실행"은 현재 구조에서 **이미 불가능**하며, 이는 러너 경로를 유지할 이유 하나(무인 병렬)를 제거한다.

### F6. 운영 사고 이력이 주는 제약

- **활성 run 워크트리 삭제 사고**(2026-08-26): "워크트리·브랜치 정리" 지시를 받은 세션이 실행 중이던 M run의 워크트리와 미푸시 브랜치를 삭제 → plan·설계·ledger 소실. **조립 형태는 동시 활성 워크트리 수를 n배로 늘리므로 이 노출을 n배로 키운다.**
- **codex 루틴 행 락 사고**(2026-08-21~24): MCP 디스패치 행 변종. 병렬 Codex 빌더가 n개면 이 사고 클래스의 발생 확률도 n배다(단, 러너 경로도 동일한 노출을 가진다 — 조립 고유의 신규 리스크는 아니다).

## 4. 타깃 형태 — 3단 구성 (Q1: harnie ↔ native 경계)

L은 **파이프라인이 아니라 조립(composition)** 이 된다.

```
[1단 · harnie 소유] 설계 run  (빌드하지 않는 run)
    그라운딩 → (ARCH → Codex DR) → 태스크 분할 초안 → 태스크 스코프 그라운딩
    → CONTRACT 작성 → Codex DR → 승인 게이트 1회
    산출물: CONTRACT + **디스패치 팩**(단위별 자립 프롬프트 n개)

[2단 · native 소유] 실행 — 단위 n개, 각각이 독립 harnie run
    단위 i = 별도 체크아웃에서 `/harnie:dev <디스패치 프롬프트 i>` → **M run**
    (자기 sentinel · 자기 owner session · 자기 baseline/seal/ledger/receipt/completion)
    병렬화·격리·재개는 native(별도 세션 또는 Agent/Workflow worktree 격리)가 담당

[3단 · harnie 소유] 통합 run  (얇음)
    단위 브랜치 순차 병합 → 병합 delta에 CR 1라운드 → `verify --integration` 1회
    → Final Review 1유닛(4렌즈) → completion
```

### 4.1 경계표

| 관심사 | 소유 | 근거 |
|---|---|---|
| 요구 그라운딩·ARCH·CONTRACT 설계 | **harnie** | 크로스모델 DR이 걸리는 지점. 팀 설계(`team-collab.md` §1)가 적용되는 유일한 구간 |
| 승인 게이트(무엇을 만들 것인가) | **harnie** | `arm-approval` 원샷 바인딩 = 자기승인 차단 불변식 |
| 디스패치 팩 작성 | **harnie** | CONTRACT의 파생 산출물. 단위 프롬프트의 자립성이 곧 컨텍스트 격리 |
| **병렬 스케줄링·워크트리 격리·재개** | **native** | `Agent isolation:'worktree'`, `Workflow parallel/pipeline`, `resumeFromRunId` — harnie가 만들 이유 없음. 0.11 §2 비목표("스케줄러·의존성 그래프 실행기 금지")와도 정합 |
| 단위 내부 설계·빌드·코드리뷰·검증 | **harnie(M 경로)** | 단위 = 평범한 M run. **신규 계약 0개** |
| 단위 간 순차 통합·전체 스위트·Final Review | **harnie** | 트리 바인딩 receipt·완료 유도가 여기에 있다 |
| 정직 보고(HARNIE_STATUS) | **harnie** | run마다(총 n+2회) 각자 정직 |

### 4.2 "단위 = M run"이 강제되는 이유

F4-3에 따라 단위가 자기 run을 갖지 않으면 강제가 0이다. 자기 run을 갖는 순간 **S/M에 이미 있는 모든 계약이 공짜로 따라온다**: 승인 전 쓰기 차단(H1) · 빌더 threadId 귀속 · watchdog · seal/seal-verify · `capture --record` baseline · delta 스코프 귀속 · ledger fail-closed · TASK-DETAIL 설계 + Codex DR · Claude CR 루프 · `verify` receipt · Stop 훅 완료 유도.

즉 **조립 형태의 실행 계층은 신규 계약을 하나도 요구하지 않는다.** 이것이 이 안의 핵심 논거다 — 러너 경로가 발명한 것(브리프·재개표·카나리아 핸드셰이크·wave·인라인 리뷰어 정당화 예외)은 전부 "M run이 아닌 무언가"를 만들었기 때문에 필요했던 부품이다.

### 4.3 부수 효과 — 사라지는 위험

- **seal 인터리빙 위험 소멸**(0.10 §11.4, 이 run에서 오탐 3회): seal은 run 전체 스코프다. run당 단위가 1개면 다른 유닛의 `apply`/`verify`가 대기 중인 seal을 무효화하는 상황이 **구조적으로 발생하지 않는다.**
- **ledger 네임스페이스 혼동 소멸**(0.10 §11.3, 오배치 2회): 유닛 ledger가 물리적으로 다른 run에 있으므로 ID 교차 오기입 경로가 없다.
- **컨텍스트 예산**: 오케스트레이터 1개가 n개 유닛의 고정비를 누적하던 구조(hmm의 지배 비용)가 n개 세션으로 분산된다.

## 5. 통합 검증 단계의 증거 계약 (Q2: 유지할 최소)

통합 run이 답해야 하는 질문은 정확히 셋이다. **① 병합된 각 브랜치는 실제로 완주한 단위 run의 산출물인가 ② 병합 자체가 만든 변경은 리뷰되었는가 ③ 최종 트리는 전체 스위트를 통과했는가.**

### 5.1 유지 (기존 계약 그대로, 신규 없음)

| 계약 | 출처 | 통합 run에서의 형태 |
|---|---|---|
| ledger fail-closed `apply` (CR·DR 공통) | `loop.md` / `loop.mjs` | 병합 delta 리뷰·Final Review에 그대로 |
| `capture --record` baseline + `delta` 스코프 귀속 | driver R1 | 병합 전 `mergeBaselineSHA` 캡처(현행 L 6단계와 동일) |
| seal / seal-verify | DR-003 사고 유래 | 통합 run에도 생산자 윈도(충돌 해소 빌더 호출)가 있으면 그대로 |
| `verify --integration` 유효 키 3요소(whole-tree 아티팩트 ‖ planHash ‖ 항목 정규화 해시) + vacuous 검출 + 무변화 재실행 거부 | 0.11 §6-b | **무변경 유지.** "최종 트리에 바인딩된 성공 receipt 정확히 1개" |
| Final Review 1유닛 4렌즈(coverage·quality·runtime·scope), **테스트 재실행 금지** | 0.11 §6.3 | 무변경 유지. runtime 렌즈 = 통합 receipt 참조 |
| `execution.mjs completion` 유도 + Stop 훅 | 불변식 ② | 무변경 유지 |
| 승인 게이트 | A5 | 통합 run의 매니페스트(= 병합 단위 목록 + `integrationVerification`)에 1회 |
| 사람검증 체크리스트 인계 | 0.11 §6.5 | 각 단위 run의 체크리스트를 통합 run이 합산 인계 |

### 5.2 이 형태가 새로 요구하는 유일한 증거 — 단위 완주 증명

**문제**: 단위 run의 증거(ledger·receipt·completion)는 그 단위의 워크트리 `.harnie/plan/<slug>/` 안에 있다. 통합 run은 **브랜치만** 본다. 검증 없이 병합하면 **STALLED 상태로 방치된 단위, 리뷰 미승인 상태의 커밋, 검증 receipt 없는 단위**가 조용히 최종 트리에 들어오고, Final Review는 병합된 트리만 보므로 이를 구별할 수 없다 — **거짓승인 경로**이며, 현행 L의 "확인 리뷰"가 막고 있던 바로 그 구멍이다.

**최소 해법 — 두 단계로 나눈다.**

- **0.13(신규 메커니즘 0개)**: 통합 run의 매니페스트가 단위마다 `unitEvidence: { workroot, slug, headSHA }`를 선언하고, 오케스트레이터가 병합 **전에** 그 경로에서 단위 run의 `completion` 출력을 읽어(읽기는 공인 경로) **`complete === true` ∧ `headSHA === 병합 대상 브랜치의 tip`** 을 확인한다. 불일치면 병합하지 않는다. 이는 문서 계약이며 기계 강제가 아니다 — **한계를 명시적으로 기록한다.**
- **0.14 이후(실측 2회 후에만)**: `execution.mjs export-completion --root <unitWorkroot> --slug <slug> --out <file>` 신설 + 통합 run의 `validateManifest`가 그 파일의 서명·`headSHA` 일치를 fail-closed로 검사. **구체적 실수 시나리오**(위 문단)가 이미 서술돼 있으므로 이 메커니즘은 contest 게이트의 `overengineering` 기각 대상이 아니다 — 다만 **실제로 그 실수가 관측된 뒤에** 만든다(rule of three가 아니라 rule of one: 거짓승인은 1회 관측으로 승격할 만큼 심각하다).

### 5.3 병합 리뷰의 깊이 — 현행 L보다 얕게

현행 L 6단계는 병합마다 **확인 리뷰 유닛 전체**(confirmation tier, mergeBaselineSHA 기준 delta, 직전 유닛 verdict 컨텍스트)를 돈다. 조립 형태에서는 단위 run이 이미 자기 delta를 완전히 리뷰·승인했으므로 **중복**이다. 대신:

- 병합 커밋 자체가 만든 변경(충돌 해소 + 시맨틱 드리프트)에 대해 **CR 1라운드**. 충돌이 0이고 delta가 순수 fast-forward성이면 라운드 없이 기록만.
- 단위 간 정합성(계약 위반·중복 구현·인터페이스 드리프트)은 **Final Review의 coverage·scope 렌즈**가 담당한다 — 4렌즈 체크리스트는 그러라고 만든 것이다.
- **불변식 보존**: "모든 수정은 리뷰된다"는 유지된다(병합 커밋은 수정이고, 그 delta가 리뷰 대상이다).

**미검증 가정**: 확인 리뷰 전체를 병합 delta 1라운드로 줄여도 안전한지는 데이터가 없다(L이 돈 적이 없으므로 확인 리뷰의 실효도 미측정). → **U-C**.

## 8. 반대 논거 (Q5)

**C1 — 미측정을 미측정으로 교체한다.** L은 Codex ARCH 리뷰 4라운드 + 상세 리뷰 2라운드를 흡수한 설계다. 그것을 실측 0건으로 폐기하고, 역시 실측 0건인 조립으로 바꾸는 것은 근거의 질이 동등하다. — **부분 반박**: 조립은 실행 이력이 있는 M 경로의 n중 재사용이라 부품 단위 분산이 낮다(§1-3). 그러나 **부품이 검증됐다고 조립이 검증되는 것은 아니다.** 이 반론이 Stage 1 파일럿을 필수 게이트로 만든 이유이며, 이 반론 때문에 권고안은 **삭제가 아니라 동결**이다.

**C2 — 실행 중 전역 시야가 사라진다 (가장 강한 반대).** L에서는 메인이 CONTRACT를 쥔 채 러너들의 종료 보고를 모두 본다 → 태스크 간 드리프트를 조기에 포착하고, 두 러너가 같은 계약 절을 문제 삼으면 그것이 CONTRACT 결함임을 즉시 안다. 조립에서는 n개 세션이 각자 자기 프롬프트만 본다 → **드리프트가 병합 시점까지 잠복**하고, 그때는 수정 비용이 가장 비싸다. `contract-conflict`를 보고할 중앙이 없다는 점도 실질적 후퇴다. **완화안(전부 비용 있음)**: ⓐ 아무것도 안 함(병합에서 발견) ⓑ 단위 run이 계약 충돌을 공유 파일에 append하고 설계 세션이 폴링 ⓒ 통합 전 read-only "계약 정합" 스카우트 1회. → **U-D. 이 문서는 답을 정하지 않는다.**

**C3 — 사람 게이트가 n배가 된다.** 현행 L은 승인 1회로 전체를 커버한다. 조립은 설계 1 + 단위 n + 통합 1 = **n+2회**. n=4면 6회 — 운영자 1인에게는 명백한 후퇴일 수 있다. 검토한 완화안: (ⅰ) 단위를 **S 사이즈**로(승인 게이트 없음) — 그러나 S는 TASK-DETAIL 설계·DR도 건너뛴다. hmm w7의 9라운드 근인이 바로 이 층의 사실 누락이었으므로 **부적절**. (ⅱ) **mode `U`**(= M − 승인 게이트) 신설 + 디스패치 파일 해시가 승인된 CONTRACT의 디스패치 인덱스에 있을 때만 시작 허용 — 승인은 CONTRACT에서 이미 일어났다는 논리. 자기승인 차단 불변식과의 정합성은 "해시가 사용자 승인된 문서에 바인딩된다"로 유지된다. **그러나 이것은 신규 모드 + 신규 바인딩이고, 파일럿 전에 만드는 것은 overengineering이다.** → 0.13 비포함, **U-B**.

**C4 — Workflow 경로는 빌드에 적합한지 미검증.** Workflow 에이전트가 다중 라운드 빌드 동안 Codex MCP 스레드를 유지할 수 있는지, 부모 세션 cwd 기준의 훅 root 해석이 격리 워크트리와 어긋나지 않는지, Workflow 자체의 resume 모델이 harnie의 디스크 기반 재개와 충돌하지 않는지 — 전부 미측정. **따라서 이 문서는 실행 계층의 기본을 "독립 대화형 세션"으로 두고 Workflow는 설계 단계 팬아웃(스카우트 n개)과 파일럿의 기계 점검에 한정 권고한다.**

**C5 — 워크스페이스 지원은 사라지지 않는다.** 멀티레포 기계(`repo-add`·`ws:` 합성·entry별 `repo`)는 통합 run으로 **이전**될 뿐이다. "L 해체 = 워크스페이스 코드 삭제"로 읽으면 과장이며, 감량 기대치를 부풀린다.

**C6 — 사고 노출의 n배 증가.** 동시 활성 워크트리 n개 → F6의 삭제 사고 노출이 n배. 0.13 백로그 #4(run 워크트리 lock 마커)가 **이 안의 선행 조건**이 된다.

**C7 — 순서 의존.** 0.13 백로그 #2(엔진 관료제 감량)를 먼저 하면 해체가 지울 코드를 먼저 심사하는 낭비다. **해체 → 감량 순서**가 맞다.
