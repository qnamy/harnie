# harnie 0.11 — 개발 프로세스 전면 재설계 (아키텍처 설계, rev-6)

> 상태: 초안(사용자 승인 전) · 고도: 아키텍처 · 작성 근거: fcl-hmm 런 실측 + harness-digest 결과 + 0.10 강제장치 인벤토리 + 사용자 확정 결정 4건
> 위협 모델(0.10 계승): **실수하는(fallible), 과열심인 오케스트레이터/빌더**. 세션-적대적 메인 에이전트 방어는 비목표.

## 1. Executive Summary

0.10 dev-full은 태스크를 과도하게 잘게 쪼개고, 태스크마다 전체 리뷰 루프·테스트를 반복하며, run-level 단일 상세설계 문서가 비대해져(2,529줄) 시간과 토큰을 과소비한다. fcl-hmm 런 실측: **태스크 14개 → 리뷰 유닛 19개 → 리뷰 라운드 73회, 이슈 182건, 전체 테스트 스위트 9회 이상 실행 + 파이널에서 전량 재실행** — 전 구간이 serial 경로(공유 워크트리, 오케스트레이터 인라인)로 수행되어 병렬 러너 경로는 가동조차 되지 않았고, Codex 세션 유실로 인한 수동 복구가 6회+, 워치독 연장이 9회 발생했다(harness-digest).

0.11은 프로세스 골격을 재설계한다. 핵심 5가지:

1. **단일 파이프라인, 크기별 스테이지 스킵** — quick/full 2트랙과 라우터를 폐지하고, `요구분석 → (아키설계 → 리뷰) → (태스크 분할) → 상세설계 → 리뷰 → 구현 → 리뷰 → 검증` 단일 골격에서 작업 크기(S/M/L)에 따라 괄호 스테이지를 스킵한다.
2. **상세설계의 분산** — L(대형)에서 run-level 상세설계를 폐지한다. 중앙에는 **공통 계약 문서**(태스크 간 인터페이스·데이터 계약)만 얇게 남기고, 각 태스크의 내부 상세설계는 태스크 러너가 병렬로 수행한다.
3. **태스크 최소 크기 + 테스트 실행 계약(hard rule)** — "독립 리뷰 가치" 미달 태스크는 병합을 강제하고, 태스크 단계에서는 스코프 테스트만, 전체 스위트는 통합 후 1회만 실행한다.
4. **리뷰 이의(contest) 게이트** — 고도 이탈(아키 리뷰가 상세설계로 하강 등)·근거 없는 메커니즘 추가(과설계/오버엔지니어링) finding에 대해, 수정하는 대신 **이의를 제기하고 리뷰어의 다음 응답 1회로 판정을 끝내는** 고속 경로를 계약화한다. 리뷰어가 고수하면 스태그네이션 라운드를 태우지 않고 즉시 사용자 에스컬레이션. 정확성·안전·미검증 리스크 finding은 이의 대상이 아니다. 종결 권한은 리뷰어와 사용자에게만 있다(오케스트레이터 일방 종결 없음).
5. **지침 문서의 must/must-not 재작성 + Codex 단독 커맨드** — 모든 에이전트·스킬 문서를 "필수/금지/나머지는 자율" 구조로 재작성해 절차 서술을 걷어내고, Codex에서 Claude 서브에이전트 없이 완주하는 단독 스킬(cross-model 리뷰 우선, 셀프리뷰 폴백)을 신설한다.

**최대 리스크 3건**: ① 이의 게이트가 남용되어 리뷰가 무력화될 가능성 → 종결 권한을 리뷰어·사용자에게만 두고(일방 종결 없음) receipt·최종보고·digest 감사 유지(§6.4). ② 태스크별 상세설계가 태스크 간 계약 불일치를 낳을 가능성 → 공통 계약 문서를 승인 게이트 산출물로 격상(§6.2). ③ 전면 재작성 과정에서 사고 유래 불변식이 소리 없이 탈락할 가능성 → §8 disposition 표로 27개 장치 전수 처분을 명시.

## 5. 권고 아키텍처 — 0.11 파이프라인

**진입**: `/harnie:dev <task>` 단일 커맨드. 커맨드는 크기·난이도만 판정하고 즉시 파이프라인 스킬로 진입한다(별도 라우터 문서 폐지).

**크기 판정(S/M/L)** — 스테이지 스킵의 유일한 축. 난이도(easy/medium/hard)는 모델 티어용으로 별도 유지(0.10 계승). **판정은 2단계다**: 진입 시의 판정은 **잠정값**이고, 그라운딩(스카우트 결과)을 본 뒤 확정해 기록한다. 확정 이후라도 후속 단계에서 상위 크기의 조건이 드러나면(예: S로 진행하던 버그픽스가 조사 중 데이터 소유권 변경으로 판명) **즉시 상위 크기로 승격하고 건너뛴 선행 스테이지(아키설계·승인 게이트)를 소급 수행**한다 — 하향 재분류는 없다(이미 수행한 스테이지는 낭비가 아니다). **승격 시 이미 소스 변경이 존재하면(S에는 승인 게이트가 없으므로 가능)**: S도 빌더 첫 호출 전 트리 baseline을 캡처하므로(현행 quick과 동일), 승격 delta는 **그 baseline 이후의 에이전트 소유 변경으로 한정**해 캡처하고 승인 자료에 "기존 작업물"로 명시 첨부한다 — 사용자가 승인하면 delta의 행선지는 승격 목적지에 따라 갈린다 — **M 승격**: 첫(유일) 리뷰 유닛의 리뷰 대상에 그대로 포함. **L 승격(태스크·worktree 분할)**: 기본값은 delta를 패치로 보존하고 트리에서 제거한 뒤 **승인된 baseline에서 재구현**(보존 패치는 해당 태스크 빌더의 참고자료로 제공 가능 — S에서 쓴 코드는 정의상 소규모다); delta가 **단일 태스크 scope에 완전히 귀속될 때만** 그 태스크 worktree의 시작점으로 반입해 해당 리뷰 유닛의 리뷰 대상에 포함한다. 여러 태스크 scope에 걸친 delta를 run 브랜치에 선반영하는 것은 태스크별 리뷰 우회이므로 금지. 거부하면 그 delta만 revert한다. S 시작 시점에 이미 더럽던 트리(사용자·타 에이전트 변경)는 소유권이 섞인 것이므로 **자동 revert 금지 — 파일 목록과 상태를 사용자에게 인계**한다(빌더 실패 복구의 귀속 안전 규칙과 동일). 승인 전 신규 소스 쓰기 차단(H1)은 승격 순간부터 정상 적용된다.

- **S(소형)**: 국소 버그픽스·소규모 변경. ARCH 트리거 없음, 태스크 분할 없음, 설계 문서가 불필요할 만큼 자명.
- **M(중형)**: 설계 판단이 필요하지만 태스크 분할이 불필요(단일 리뷰 유닛으로 충분).
- **L(대형)**: ARCH 트리거 존재 또는 독립 리뷰 가치가 있는 태스크 2개 이상.

**파이프라인(굵게 = 모든 크기 공통, 괄호 = 조건부)**

```
요구분석·그라운딩(스카우트 병렬) ─ 질문(필요시)
  → (L: 아키설계 → Codex 아키리뷰 루프)            … 아키 고도 렌즈만
  → (L: 태스크 분할 초안 → 태스크 스코프 그라운딩(read-only 스카우트 병렬: 각 태스크의
       코드 경로·기존 테스트·런타임/드라이버 시맨틱스) → 그 결과로 scope·검증 명세를 확정한
       공통 계약 문서 → Codex 리뷰)                  … 분할 근거 필수, 계약은 근거 위에서 확정
  → (M·L: 승인 게이트 — 1회, planHash 바인딩)
  → 구현 단위 실행:
      S·M: 인라인 — (M: 경량 상세설계 → Codex 리뷰 1라운드~) → Codex 빌드 → Claude 코드리뷰 루프
      L:   태스크 러너 병렬 — 러너가 태스크별 [증분 그라운딩(브리프에 담긴 태스크 팩트의 검증
           + 잔여 시맨틱스 확인 — 승인 전 태스크 스코프 그라운딩의 재수행이 아님) → 상세설계
           → Codex 설계리뷰 → Codex 빌드 → Claude 인라인 코드리뷰 → 커밋]을 자기 워크트리에서 완주
  → (L: 순차 통합 + 확인 리뷰)
  → 검증: 자동(전체 스위트 1회 + receipt) / 사람(체크리스트 인계)
  → (L: Final Review 1유닛 — 4렌즈 체크리스트) → 완료 재유도(HARNIE_STATUS)
```

cross-model 대칭은 전 크기·전 스테이지에서 불변: **설계 = Claude 생산 → Codex 리뷰, 코드 = Codex 생산 → Claude 리뷰**.

## 6. 핵심 결정

### 6.1 고도 계약 — 아키 / 공통 계약 / 태스크 상세

문서·리뷰 고도를 3층으로 재정의한다(0.10은 2층: ARCH/DETAIL).

| 층 | 내용 | 생산자 | 리뷰 렌즈 |
|---|---|---|---|
| **ARCH** | 경계, 컴포넌트, 데이터 소유, 기술 선택, SPOF | designer(fable) | 아키 렌즈만 — 클래스·SQL·태스크 내부 로직 finding은 기각 대상 |
| **CONTRACT**(신설) | 태스크 간 인터페이스·데이터 계약, 태스크 분할안·분할 근거, 태스크별 검증 명세(자동/사람) | designer | 계약 완전성·태스크 간 정합만 — 태스크 내부 구현 finding은 기각 대상 |
| **TASK-DETAIL** | 태스크 내부 로직·데이터·테스트 설계(경량 프로파일). 입력 = 브리프의 태스크 Environment Fact Sheet(승인 전 태스크 스코프 그라운딩의 산출 — 코드 경로·기존 테스트·런타임/드라이버 시맨틱스, 예: DB 드라이버의 배치 스코프 SET 옵션, datetime 절삭. hmm w7 9라운드의 근인이 이 층의 사실 누락) + 러너의 **증분 그라운딩**(팩트 검증·잔여 확인) | 러너(Claude) | 결정 완전성·실패 모드 — 계약 변경 요구는 이의 대상(계약 변경은 중앙 경로로 에스컬레이션) |

근거: hmm의 2,529줄 rev-6은 CONTRACT와 TASK-DETAIL 14개분이 한 문서에 눌려 있던 것이다. 분리하면 ① 설계 리뷰가 병렬화되고 ② 리뷰어가 매 라운드 100k 토큰 문서를 다시 읽는 비용이 사라지며 ③ 고도 이탈 기각의 판정 기준이 문서 경계와 일치한다.

CONTRACT 문서는 승인 게이트 산출물이며, **태스크 스코프 그라운딩(승인 전, read-only 스카우트 병렬) 위에서 scope·검증 명세를 확정한다** — 근거 없이 확정된 계약이 러너의 뒤늦은 발견으로 반복 무효화(A5.2 재승인 왕복)되는 것을 막는다. 태스크 상세설계는 승인 후 러너가 작성하고 러너의 Codex 설계리뷰가 게이트한다 — **계약을 벗어나는 설계는 러너가 진행할 수 없고 중앙 에스컬레이션**(0.10 errata의 축소 계승, §8).

### 6.2 태스크 최소 크기 (hard rule)

태스크로 분리하려면 **필수 조건**을 충족해야 한다: **독립 리뷰 가치** — 변경의 규모·위험이 그 자체로 리뷰 유닛 1개의 고정비(설계리뷰+빌드+코드리뷰 배선, ledger, 스코프 테스트)를 정당화할 것. 이 조건을 만족하는 후보들 사이에서만 deps 순서·병렬 격리 이득이 **분리의 보조 근거**가 된다 — deps나 병렬성 단독으로는 태스크가 되지 못한다(10라인짜리 선행 설정 변경은 그것을 기다리는 첫 태스크의 첫 단계로 병합한다). 필수 조건 미충족 시 **가장 관련 있는 인접 태스크에 병합 — 예외 없음**.

- 정량 보조선: 예상 diff 100라인 미만이거나 스코프 1~2파일이면 병합이 기본값(반증 근거를 CONTRACT에 기재할 때만 분리 허용).
- CONTRACT 문서의 분할안에는 **태스크마다 필수 조건 충족 근거 1줄 명기**가 필수이고, 승인 게이트에서 사용자가 본다.
- 근거: hmm 14태스크 중 다수가 리뷰 유닛 고정비를 정당화하지 못했다(w0 매니페스트 3라운드, w11 알림 1라운드짜리 유닛 등 — serial 경로였으므로 이 고정비 전액이 오케스트레이터 컨텍스트에 누적됐다). 같은 작업을 이 규칙으로 재분할하면 6±2개로 수렴한다.

### 6.3 테스트 실행 계약 (hard rule)

- **태스크 단계(러너·빌더)**: CONTRACT가 태스크별로 명시한 **스코프 테스트 집합만** 실행한다. baseline 실측(수정 전 1회)도 그 집합으로 한정. 빌더 프롬프트 must-not: "스코프 밖 스위트 실행 금지".
- **전체 스위트의 목표 상태는 "횟수 1회"가 아니라 "최종 트리에 바인딩된 성공 receipt 정확히 1개"다.** 통합 완료 후 전체 스위트+저장소 컨벤션 검사를 실행해 receipt를 남긴다. 이후 코드가 변경되면(전체 스위트 실패로 인한 수정, Final Review finding 반영 포함) 기존 receipt는 트리 불일치로 **자동 무효**이고 수정 완료 후 재실행한다 — 이는 규칙 위반이 아니라 규칙의 작동이다. **금지되는 것은 트리 변화 없는 중복 재실행**(같은 상태를 다시 확인하는 실행)과, 태스크 단계에서의 전량 실행이다.
- **Final Review는 테스트를 재실행하지 않는다** — 현재 트리에 바인딩된 통합 receipt를 참조한다. (hmm W14가 태스크로 전체 재검증을 중복 수행 + 파이널 게이트가 또 확인한 낭비 제거. "전체 재검증"성 태스크는 매니페스트 등록 금지.)
- 검증 receipt·vacuous 검출·A5.0 증거 계약은 0.10 그대로 계승한다(§8).

### 6.4 리뷰 이의(contest) 게이트 — 신규 메커니즘 없이 기존 경로 재조합

**해결하는 구체적 실수 시나리오**: hmm·fcl 런에서 리뷰어의 메커니즘 추가 요구를 라운드마다 "어떻게 만족시키나"로만 받아 claim·lease·hash가 누적되고, 이를 해체하는 데 다시 여러 라운드를 소모했다(0.10 문서에 명시 관측). 반대 방향의 실수도 있다: 피리뷰 당사자(오케스트레이터·러너)가 blocking을 일방 종결할 수 있으면, 공유 계약을 깨는 동시성 오류를 "고도 밖"으로 오분류해 닫는 순간 거짓승인이 된다(rev-1의 `--reject` CLI 동사가 이 결함을 가졌고, 리뷰에서 기각되어 폐기).

**계약(신규 CLI·ledger 상태 없음 — 기존 리뷰어 종결 + human-gated 경로의 재조합)**:

1. 오케스트레이터/러너는 다음 2사유의 open blocking finding에 대해 수정 대신 **이의를 제기**할 수 있다: `altitude`(현재 리뷰 고도 §6.1 밖의 요구), `overengineering`(메커니즘 추가 요구인데 그것이 방지하는 구체적 실수 시나리오가 제시되지 않음 — design-review.md의 입증 책임 규칙을 소비 측에서 집행).
2. 이의는 다음 리뷰어 호출(stateful 스레드)에 사유와 함께 전달되고, **리뷰어의 그 응답 1회로 판정이 끝난다**: 리뷰어가 수긍하면 해당 ID를 `resolved`로 닫고 필요시 non-blocking 신규 ID로 재등록(기존 ledger 규칙 그대로), 고수하면 **즉시 사용자 에스컬레이션** — 스태그네이션 라운드를 태우며 설득을 반복하지 않는다(human-gated blocking의 "루프 금지, 에스컬레이션" 규칙을 이의 불일치에 일반화). 사용자가 리스크를 인수하면 기존 `user-decision` 해제 경로 그대로 처리한다.
3. **이의 불가 클래스**: 정확성·안전·미검증 리스크 finding("이 입력에서 이 경로가 깨진다/검증되지 않았다"류)은 위 2사유에 해당할 수 없다 — 문서 계약이며, 오분류를 리뷰어 응답(종결 권한 보유자)과 receipt·최종보고·harness-digest 감사가 이중으로 잡는다.
4. 종결 권한은 변하지 않는다: **ledger의 ID를 닫는 것은 언제나 리뷰어 응답 또는 사용자 결정**이고, 오케스트레이터는 이의를 기록·전달할 뿐이다. 이의 제기·판정·에스컬레이션 전량이 receipt에 남는다.

FR-2("리뷰 내용을 전부 반영하지 않는다")의 지지대는 이 고속 판정 경로다: 부당한 blocking 하나의 비용이 "설득 라운드 N회"에서 "리뷰어 응답 1회 or 사용자 판단 1회"로 상한된다.

### 6.5 검증 계약 — 자동/사람 분리

CONTRACT(L) 또는 설계·계획 노트(S·M)에 검증 항목을 처음부터 2열로 기재한다:

- **자동**: manifest `verification[]` → receipt·vacuous 검출(0.10 계승).
- **사람**: 자동화가 확인 못 하는 사용자 가시 행위·외부 시스템 대조 — **항목·확인 방법·리스크**를 명시한 체크리스트로 작성하고, 완료 보고가 이 체크리스트를 그대로 인계한다. 사람 항목은 receipt 없이는 "검증됨"으로 집계하지 않는다(HARNIE_STATUS에는 `needs-human-verification: N건`으로 표기).

근거: verification-tiers의 Manual QA 규칙이 이미 존재하나 "미리 나눠 인계"가 없어, 사람 확인 필요 항목이 완료 보고에 묻혔다.

## 7. 문서 재작성 계약 (FR-9)

모든 `agents/`·`skills/`·`instructions/` 문서를 다음 구조로 재작성한다:

1. **역할·목표** — 1문단.
2. **MUST** — 불변식·산출물 계약·게이트. 각 항목은 한 줄 + (사고 유래면) 근거 한 줄.
3. **NEVER** — 금지 목록(과설계·스코프 초과·고도 이탈·자가승인류).
4. **산출물 계약** — 스키마/경로/보고 형식.

절차 서술("~한 다음 ~를 하라" 체인)은 오케스트레이터 스킬 1곳에만 남기고 대폭 압축한다. **판단 방법은 지시하지 않는다** — 무엇이 필수이고 무엇이 금지인지만 계약하고 방법은 에이전트 자율(FR-9의 "창의성" 요구). 영어 정본 + `-ko` 미러 정책 유지.

**요구사항 반영 확인의 위치(사용자 지시로 판정)**: 요구 커버리지 확인은 **리뷰 기준 한 줄로만 유지**하고("미커버 요구는 blocking" — 비용이 거의 없고 under-building을 막는 유일한 렌즈), **산출물 강제는 폐지**한다 — 설계 프로파일의 요구 추적성 매트릭스(요구 ID→모듈→테스트→모니터링 표)를 필수 섹션에서 제외하고, FR/NFR ID 체계 부여도 유용할 때만 에이전트 자율로 둔다. 커버리지 검토 자체는 에이전트가 자연 수행하며, 강제된 표는 문서 비대(2,529줄 사례)에 기여했을 뿐 라운드 절감 증거가 없다.

## 9. 핵심 시나리오

**S — e1ct급 버그픽스**: 그라운딩 → (설계 스킵) → Codex 빌드(스코프 테스트 baseline) → Claude 코드리뷰 루프 → 자동 검증 + 사람 체크리스트(있다면) → 보고. 승인 게이트 없음. 리뷰 1유닛. 현행 quick과 유사하되 문서가 must/must-not로 얇아진 형태.

**L — hmm급 이관**: 그라운딩 → 아키설계+아키리뷰(아키 렌즈, 하강 finding 기각) → 태스크 분할(최소 크기 규칙, 근거 명기)+CONTRACT+리뷰 → 승인(1회) → 러너 N개 병렬[태스크 상세설계→Codex 설계리뷰→빌드→인라인 코드리뷰(스코프 테스트만)→커밋] → 순차 통합+확인리뷰 → 전체 스위트 1회 → Final Review 1유닛 → 사람 체크리스트 인계 → 완료 재유도.

**실패 플로우 — 리뷰어가 CONTRACT 리뷰에서 태스크 내부 구현을 blocking으로 요구**: 오케스트레이터가 다음 리뷰어 호출에 `altitude` 이의를 사유와 함께 전달 → 리뷰어가 그 응답에서 수긍(`resolved` + 필요시 non-blocking 재등록)하거나 고수 → 고수 시 스태그네이션을 태우지 않고 즉시 사용자 에스컬레이션(인수 시 `user-decision` 해제). 정확성 finding이면 이의 불가 — 정상 REVISING.
