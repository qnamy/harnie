# 검증 tier (canonical) — builder·reviewer 공통 단일 정의

이 파일이 **유일한 tier 정의**다. builder는 이 tier로 필수 검증 세트를 정하고, reviewer는 diff·영향 범위로 tier의 적정성을 **독립 판정**한다. 두 역할에 따로 복제하지 말고, 각 역할의 에이전트 본문이 **이 파일을 직접 Read하도록** 지시한다.

변경의 **실제 위험**으로 tier를 정한다 (파일 수·줄 수가 아님).

## 테스트 증거 규칙 (builder·reviewer 공통)
- **baseline 대비 pass 판정.** 이미 실패가 있는 스위트에서 절대적인 "테스트 통과" 주장은 무의미하다. 코드를 수정하기 **전에** 관련 테스트 세트를 한 번 실행해 **baseline 실패 집합**을 기록하고, 변경 후에는 **baseline 실패 수 vs 변경 후 실패 수**와 신규 실패 목록을 함께 보고한다. pass 기준은 **변경 후 실패 집합 ⊆ baseline 실패 집합**이다. 이 대조 없는 "테스트 통과" 보고는 증거가 아니다.
- **신규 테스트는 실패 가능함을 증명한다.** 구조적으로 실패할 수 없는 테스트 — 대상 동작이 깨져도 assertion이 통과하는, 예컨대 검증한다고 주장하는 결과를 실제로 관측하지 못하는 테스트 — 는 아무것도 검증하지 않는다. 신규 테스트(또는 실질적으로 강화된 assertion)마다 한 번은 fail-capability를 증명한다: 대상 동작을 일시적으로 깨뜨려 테스트가 실제로 실패함을 관측하고, 복원 후 통과를 관측하며, 그 관측을 증거에 포함한다.

| tier | 정의 (위험) | 필수 검증 세트 |
|---|---|---|
| **trivial** | 동작·계약·의존성 변화 없음 | 변경파일 진단 |
| **behavioral** | 사용자/호출자가 관찰하는 동작 변화 | 진단 + 관련 테스트 + **영향받은 공개 entry point의 focused 실행/재현** |
| **cross-cutting** | 여러 경계·패키지·데이터 계약·빌드/배포 경로에 영향 | 진단 + 관련 테스트 + 빌드 통과 + **실제 통합 경계를 포함한 integration/smoke 실행** |

## Manual QA
- 자동 검증으로 확인할 수 없는 **사용자 가시 동작**이 있으면 필수.
- 필요한 실제 실행을 수행할 수 없으면 **"검증됐다"고 간주하지 않고**, 미검증 범위와 원인을 명시한다.
- **사람 검증 항목은 사전에 분리하고**(플랜의 검증 전략에서) 완료 보고에서 체크리스트 — 항목, 확인 방법, 위험 — 로 인계한다; 사람의 확인 없이는 절대 "검증됨"으로 세지 않는다(`needs-human-verification: N`).

## 검증 불가 ≠ 검증 불필요
- 승인에 필요한 위험이 미검증 상태면, 정직하게 공개했더라도 **merge-ready 관점에서 REJECT** 대상이다.

## 해당 검증 유형이 프로젝트에 없을 때
- 필요한 검증(테스트·integration·smoke 등)이 프로젝트에 존재하지 않으면 **단순 생략하지 않는다.**
- **동등한 위험을 다루는 대체 검증**(수동 재현·계약 확인·로그/카운트 상태 대조 등)으로 커버하고, **무엇으로 대체했는지 명시**한다. 대체가 원래 위험을 다루지 못하면 미검증으로 본다.
