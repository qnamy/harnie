# 설계 작성 프로필 — 상세 고도 (canonical, 주입용)

`harnie-designer`가 **상세 설계**를 산출할 때의 **출력 계약**이다. 오케스트레이터가 이 파일의 **절대 경로를 위임 프롬프트에 전달**한다; designer는 **반드시 먼저 이 파일을 Read**해야 한다(에이전트 body는 페르소나·시작 게이트·작업 원칙만 소유 — 여기서 재서술하지 않는다).

**고도**: 아키텍처 결정을 실제 코드로 변환. 개발자가 **추가 핵심 판단 없이 구현을 시작**할 수준으로 구체화하되, **불필요한 클래스·패턴을 만들지 않는다.**

**상위 아키 준수**: 상위 아키텍처가 있으면 그 요구 ID·컴포넌트명·데이터 소유권을 **그대로** 쓴다. **아키 결정을 조용히 바꾸지 않는다** — 바꿔야 하면 "아키텍처 변경 요청"으로 분리(이유·영향). 상위 아키가 없으면 지어내지 말고 `[미결정]`.

**컴포넌트 크기 게이트**: 대상이 한 문서에 담기 너무 크면(예: API 10개 초과·독립 유스케이스 다수) 전체를 쓰지 말고 **하위 단위 분할안**을 먼저 제시하고 어디부터 쓸지 확인받는다.

**모드 스위치**: 기본 = **경량**(§경량 출력만). 호출자가 **"정식으로"** 신호할 때만 §정식 출력(전체 섹션). 두 모드 모두 body의 깊이 차등·투기 금지·중복 억제·계약 단일 출처를 적용한다.

## Environment Fact Sheet (두 모드 공통)
설계가 런타임 환경에 의존하거나 환경의 제약을 받으면, 설계 서두에 **Environment Fact Sheet**를 둔다: 설계 결정이 딛고 선 사실들을, **각각 실제 레포에서 검증하고 출처 경로를 인용해** 기록한다 — 절대 추정하지 않는다. 틀린 환경 전제는 설계리뷰 라운드 낭비의 최대 원인이다. 최소 카테고리는 생태계 중립으로 다음과 같다(정말 무관한 카테고리만 생략):
- **스키마 마이그레이션 상태** — 도구와 현재 head(예: 최신 마이그레이션 버전 식별자).
- **테스트 인프라** — 사용 가능한 러너, 컨테이너/픽스처, 이미 실패 중인 테스트의 baseline.
- **설계를 제약하는 런타임 설정** — 타임아웃, 풀, 설계의 전제 범위를 한정하는 프레임워크 설정.
- **설계가 전제하는 프레임워크/빌드 도구 동작** — 프록시/AOP 시맨틱, 빌드의 테스트 태스크가 필요한 프로퍼티를 전달하는지.
대상 레포 자체 지침을 먼저 참조한다 — 커밋된 것(`AGENTS.md`/`CLAUDE.md`)이든 개인용 미추적 파일(`CLAUDE.local.md`, 공유 레포에 커밋하면 안 되는 사실용)이든 — 도구별 구체 사실이 이미 기록돼 있을 수 있다. 호출자가 fact sheet를 제공하면(예: plan grounding 산출) 재도출하지 말고 검증 후 재사용한다. 검증하지 못한 사실 위의 결정은 추정이 아니라 `[미결정]`이다.

## §경량 출력 (기본)
1. **설계 요약** — 구현 대상·책임, 관련 FR/NFR ID, 상위 아키텍처에서의 위치, 입력·출력·의존성, 범위·비범위. 상위 ADR 있으면 참조, 없으면 `N/A`.
2. **요구사항 추적표** — 열: 요구 ID / 구현 모듈 / API·이벤트·데이터 / 검증 규칙 / 테스트 / 모니터링 지표. **커버 안 된 요구 ID·근거 없는 요소 명시.**
3. **핵심 처리 로직** — 자명하지 않은 유스케이스만: 사전조건 → 단계별 처리(필요시 의사코드) → 성공 후 상태 → 단계별 실패 후 상태·보상 → 동시 실행·중복 요청 동작.
4. **계약** — 자명하지 않은 API/이벤트만: 목적·인증인가·요청/응답 요지·오류 계약·멱등성·버전/호환성. 기계 스키마 있으면 파일·operation ID로 참조(필드 전사 금지).
5. **데이터·상태** — 변경 테이블/엔티티, 트랜잭션 경계, 동시성 제어(낙관/비관 근거), 핵심 상태 전이(필요시 Mermaid stateDiagram).
6. **작업 분해** — 각 작업: 작업명·산출물·선행작업·완료조건·테스트·위험·크기(S/M/L). 하나가 독립 리뷰/변경 단위가 되게.
7. **미결정·아키텍처 변경 요청** — `[미결정]`, 아키텍트 승인 필요 항목, 필요한 PoC, 결정 기한.

(작은 작업이면 이 계약을 몇 줄로 압축 — 장황한 섹션 강제 아님.)

## §정식 출력 ("정식으로" 요청 시)
경량 출력을 아래 전체 섹션으로 확장한다(깊이 차등·중복 억제·계약 단일 출처 그대로).
1. 설계 요약
2. 요구사항 추적표 (누락·근거 없는 요소 표시)
3. 컴포넌트 내부 구조 — 모듈/패키지 구조, 모듈 책임, 공개 인터페이스, 의존 방향, 변경 가능성 높은 지점, C4 Component/UML(Mermaid). 순환 의존·다중 책임 명시.
4. 도메인·상태 모델 — 엔티티·값 객체, 불변조건, 상태·전이(허용/금지), 전이 실패 처리, Mermaid stateDiagram
5. API 계약 (자명하지 않은 것만 완전 전개) — 목적, 메서드/경로 또는 RPC, 인증·인가, 오류 코드·본문, 멱등성, 페이지네이션·정렬·필터, 타임아웃·취소, 버전·하위호환, 요청량 제한, 개인정보 노출. 기계 스키마 별도 산출물 없을 때만 필드·타입·제약·예제 인라인, 있으면 파일·operation ID 참조.
6. 이벤트·메시지 계약 — 이벤트명·버전, 생산자·소비자, 발행 조건, 전달·순서 보장, 중복 제거, 재시도·백오프, DLQ, 스키마 진화, 재처리, 민감정보. 기계 스키마 없을 때만 인라인, 있으면 message ID 참조.
7. DB 상세 — 테이블/컬렉션, 필드·타입·NULL·기본값, PK/FK/Unique/Check, **접근 패턴에 근거한** 인덱스, 트랜잭션 경계, 잠금·동시성(낙관/비관 근거), 정합성 수준, 보존·삭제, 감사, 예상 증가량, 마이그레이션·롤백. 마이그레이션 별도 산출물 없을 때만 ER·DDL 초안, 있으면 경로·migration ID 참조.
8. 핵심 처리 로직 — 유스케이스별: 사전조건, 단계별, 의사코드, 복잡도·성능, 성공/실패 후 상태, 보상, 동시 실행·중복 요청 동작
9. 시퀀스·실패 처리 — 정상 + 실패(입력검증·권한 부족·데이터 충돌·의존 타임아웃·부분 성공·메시지 중복·재시도 한도 초과·배포 중 구/신버전 동시 요청) Mermaid sequenceDiagram
10. 오류 처리 규약 — 도메인/입력/인프라/외부 오류, 사용자 노출 vs 내부 로그, 재시도 가능성, HTTP/RPC 매핑, 추적 ID, 민감정보 마스킹
11. 보안 상세 — 인증 흐름, 권한 검사 위치, 객체 단위 접근 통제, 입력 검증·출력 인코딩, 비밀정보 관리, 암호화, 감사 이벤트, rate limiting, 공격 시나리오·방어, 로그 금지 정보
12. 관측성·운영 — 구조화 로그 필드, 메트릭 이름·단위, 트레이싱 구간, 대시보드, SLI 계산, 경보 조건, 진단 정보, 기능 플래그·kill switch, runbook
13. 성능·용량 — latency budget, 예상 QPS·동시성, 쿼리/외부 호출 수, 캐시 키·TTL·무효화, 배치 크기, 메모리·저장 추정, 부하 시험 시나리오·합격 기준
14. 테스트 설계 — 단위/계약/통합/E2E/마이그레이션/동시성·멱등성/성능/장애주입/보안. 각각 요구 ID·실패 시나리오와 연결
15. 배포·호환성 — 배포 순서, DB/API/Event 변경 순서, 구/신버전 공존, 단계적 출시, feature flag, 롤백 조건·절차, 데이터 복구
16. 구현 작업 분해 — 작업명·산출물·선행작업·완료조건·테스트·위험·크기(S/M/L). 독립 리뷰/변경 단위로 분할
17. 미결정·아키텍처 변경 요청 — 상세에서 결정 가능 항목, 아키텍트 승인 필요 항목, 필요한 실험/PoC, 결정 기한
