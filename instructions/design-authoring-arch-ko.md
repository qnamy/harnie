# 설계 작성 프로필 — 아키텍처 고도 (canonical, 주입용)

이 문서는 `harnie-designer`가 **아키텍처 설계**를 산출할 때 사용하는 **출력 계약**이다. 오케스트레이터는 이 파일의 **절대 경로**를 위임 프롬프트에 전달한다; designer는 내용을 인라인으로 받는 대신 작성 전에 **반드시 이 파일을 Read**한다. 에이전트 body가 페르소나·진입 게이트·작업 원칙만 소유하므로, 여기서 재서술하지 않는다.

**고도:** 시스템 경계와 비용이 큰 기술 결정에 집중한다. 클래스, 함수, 상세 SQL, 전체 API 스키마 같은 **구현 세부로 내려가지 않는다**; 그것들은 상세-설계 프로필 소관이다.

**모드 스위치:** 기본은 **경량**이며 경량 출력 섹션만 사용한다. 호출자가 명시적으로 **"formal"**을 신호할 때만 완전한 정식 출력 섹션을 사용한다. 두 모드 모두 에이전트 body의 비례적 깊이, 투기 금지, 중복 억제, 계약 단일 출처 규칙을 적용한다.

## 경량 출력 (기본)
1. **Executive Summary** — 비기술 이해관계자를 위한 문제와 제안, 핵심 설계 결정 3~5개, 가장 큰 위험 3개를 설명한다. 추적성이 유용할 때만 선택적으로 `DEC-001` 식별자를 붙인다.
2. **목표, 범위, 비목표, 제약** — 성공 지표를 포함한다.
3. **핵심 요구사항** — 아키텍처를 구동하는 FR과 NFR을 서술한다. 식별자(`FR-001`, `NFR-001`)는 선택이다 — 추적성이 진정으로 도움이 되는 곳에서만 쓴다(강제 ID 체계나 추적성 매트릭스 없음). NFR은 가능하면 수치화한다: SLO, latency, 동시성, 데이터 증가와 보존, RTO/RPO, 비용 한도.
4. **아키텍처 대안** — 최소 두 개의 대안을 구조, 요구 충족, 복잡도, 운영 부담, 장애 격리, 성능, 비용, 벤더 종속에 걸쳐 표로 비교한다. 각 대안이 적합한 조건을 서술한다. **비교 전에 결론을 암시하지 않는다.**
5. **권장 아키텍처** — 근거와 C4 Container 수준 Mermaid 다이어그램을 제시한다. 모든 화살표에 프로토콜, 데이터, 목적을 라벨링한다. 각 컨테이너의 단일 책임, 데이터 소유권, 동기/비동기 통신을 정의한다.
6. **핵심 시나리오** — Mermaid `sequenceDiagram`으로 정상 흐름 1개와 외부 연동 실패, 타임아웃, 부분 장애 같은 대표 실패 흐름 1~2개를 제공한다.
7. **리스크와 미결 결정** — 각 리스크에 가능성, 영향, 완화, 결정 기한을 서술한다. 미결 항목은 `[UNRESOLVED]`로 나열한다.

작은 작업이면 이 계약을 몇 줄로 압축한다; 장황한 섹션을 강제하지 않는다.

## 정식 출력 (명시 요청 시)
비례적 깊이와 중복 억제를 유지하면서 경량 출력을 아래 완전한 구조로 확장한다.
1. Executive Summary
2. 목표와 범위 — 목표, 성공 지표, 범위, 명시적 비목표, 제약, 용어
3. 요구사항 — 가용성/SLO, latency/처리량, 동시 사용자, 데이터 증가/보존, RTO/RPO, 보안/개인정보, 비용 한도, 확장 목표에 걸쳐 수치화된 FR과 NFR; 우선순위와 충돌. 식별자는 선택이다(추적성이 진정으로 도움이 되는 곳에서만 쓴다 — 강제 ID 체계 없음)
4. 시스템 컨텍스트 — 사용자, 외부 시스템, 책임, 신뢰 경계, C4 System Context Mermaid 다이어그램
5. 아키텍처 대안 — 구조, 요구 충족, 복잡도, 운영 부담, 장애 격리, 성능/확장성, 보안, 비용, 벤더 종속, 강점, 약점, 적합 조건에 걸친 표 비교
6. 권장 아키텍처 — 근거; C4 Container Mermaid 다이어그램; 컨테이너별 단일 책임; 동기/비동기 통신; 데이터 저장소와 소유권; 외부 연동; 기술·버전 원칙; 금지되는 순환 의존성
7. 핵심 시나리오 — Mermaid `sequenceDiagram`으로 외부 연동 실패, 중복 요청, 부분 장애, 타임아웃, 재시도의 정상·실패 흐름
8. 데이터 아키텍처 — 데이터 분류와 소유권; 저장, 조회, 보존, 삭제; 정합성 모델; 트랜잭션 경계; 캐시 전략; 백업과 복구; 개인정보. **상세 테이블 정의나 전체 DDL은 포함하지 않는다.**
9. 품질 속성 검토 — 운영 우수성, 보안/개인정보/규정 준수, 신뢰성/복구, 성능, 비용, 지속가능성 각각에 대해 클라우드 중립 원칙으로 "설계 선택 → 근거 → 검증 방법 → 잔여 위험"을 문서화한다
10. 신뢰성과 운영 — SLI/SLO 후보, 장애 모드, 타임아웃/재시도/백오프/서킷브레이커 정책, 용량 가정과 피크 대응, 로그/메트릭/트레이스, 알림 임계값, 배포/롤백/DR, 운영자 개입 지점
11. 보안과 위협 — 핵심 자산, 인증과 인가, 신뢰 경계, 최소 권한, 암호화와 키 관리, 감사 로그, 주요 위협과 완화, 오남용 케이스
12. 배포와 마이그레이션 — 배포 토폴로지, 점진적 출시, 하위 호환성, 데이터 마이그레이션, 롤백 조건, 현재 시스템과의 공존
13. 검증 계획 — 요구사항을 어떻게 검증할지(테스트, 부하 테스트, 장애 주입, 보안 검토, 운영 리허설); 요구사항-테스트 매핑 표는 선택이며 필수가 아니다(커버리지는 리뷰어의 렌즈로 판정한다)
14. 리스크와 미결 결정 — 가능성, 영향, 완화, 담당, 결정 기한, `[UNRESOLVED]` 항목
15. ADR — 중요 결정마다: 제목, 상태, 맥락, 검토한 대안, 결정, 트레이드오프, 재검토 조건
16. 상세 설계 핸드오프 — 각 컴포넌트의 상세 설계가 정의해야 할 API, 데이터, 상태, 오류, 동시성, 테스트
